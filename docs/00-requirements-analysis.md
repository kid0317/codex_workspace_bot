# Codex Workspace Bot 需求分析

## 1. 背景

本项目是一个本机自用的飞书 Workspace Bot，用 Go 重写旧版本地机器人，并把后端 Agent 从一次一进程的命令行调用改为长期运行的 `codex app-server --stdio`。用户在飞书单聊或群聊中发消息，Bot 根据对应 App 和频道找到本机 workspace，驱动 Codex 在该目录下完成任务，并把结果回传到飞书。

项目不是通用 SaaS 聊天服务，也不是多租户企业平台。它优先服务单个操作者在本机连接多个飞书自建应用、多个工作区和多个飞书会话的真实开发流程。

## 2. 目标用户

- 本机运行 Codex CLI、Docker 和 MySQL 的开发者。
- 已有一个或多个飞书自建应用，并希望用飞书作为 Codex 工作入口的个人操作者。
- 希望在本机保留消息、会话、任务和可观测性证据，以便排障和复盘的维护者。

## 3. 核心问题

1. 飞书消息需要可靠进入本机 Codex 工作流，并按 App、频道和 workspace 隔离。
2. 同一飞书频道内的任务必须严格串行，避免多个 Codex Turn 同时修改同一上下文。
3. Bot 需要持久保存 App 配置、频道会话、消息、附件、任务和运行结果，保证重启后可恢复到可解释状态。
4. 输出体验需要区分工作模式和陪伴模式：工作模式适合流式卡片，陪伴模式适合终态纯文本分段。
5. 本项目未来要开源，仓库中不能包含真实飞书密钥、数据库密码、Langfuse Key、Codex 登录文件或本机运行数据。

## 4. 关键约束

- 只支持 Codex 原生链路，不提供 Claude 兼容层、引擎抽象或多引擎回退。
- 使用一个 bot 管理的长期 `codex app-server --stdio` 子进程服务多个 workspace。
- 持久化默认使用 MySQL；不把 Redis、SQLite 或 PostgreSQL 作为默认路径。
- 飞书 WebSocket 是主要入口；当前个人本机部署接受已启用 App 收到的有效文本消息。
- 真实配置通过 `.env`、`config.yaml` 和 MySQL `apps` 表保存，这些真实配置不得提交。
- Langfuse 可观测性是可选能力；启用后会按个人自用裁决记录明文业务数据，但运行凭据永远不得记录或提交。

## 5. 成功标准

- 新开发者能根据 README 复制模板、填写本机配置、启动 MySQL、写入飞书 App、构建并启动 Bot。
- 仓库提交前可用命令检查确认没有真实密钥、运行数据、日志、数据库文件或本地配置被纳入 git。
- `docs/` 下存在需求分析、PRD、协议调研、概要设计、Story List 和每个 Story 的设计文档。
- Story 状态跟随代码事实：已实现、开发中、待审计和待实现必须区分清楚。
- 历史过程材料被归档，不干扰开源读者理解当前项目。
