# S10：飞书富文本列表识别与输出投递容错

> **状态**：Draft / 待实现  
> **关联概设**：[概要设计 v4.5](../02-redesign-high-level.md) §7 飞书行为、§4.4 流式输出；不改变 App Server 协议、MySQL 主 schema 或 Worker FIFO 串行化契约。  
> **依赖**：S01、S02、S04、S05；真实飞书消息事件；当前 `internal/feishu.Normalize` 文本/附件标准化逻辑；当前 work-mode CardKit 输出链路。

## 1. 一句话目标

让操作者在飞书聊天框发送包含列表、编号列表或其他富文本结构的普通消息时，Bot 能把它识别为可处理文本并进入现有 Worker/Codex 链路；同时修复 work-mode 飞书卡片/初始发送失败把已进入 Codex 的请求误中断为 `presentation_backpressure` 的问题，保证 Codex 处理和最终可见交付尽量继续。

## 2. 背景

2026-07-19 本机排障确认：`course-assistant` receiver 已连接，`/readyz` 正常，但用户在飞书发送的富文本列表消息只产生日志 `feishu_event_ignored`，没有进入 `messages` 表，也没有 `worker_accepted`、卡片或文本反馈。用户明确指出根因是飞书聊天框含富文本列表时，当前入口识别不了。

现有 `internal/feishu.Normalize` 只处理 `message_type` 为 `text`、`image` 和 `file` 的窄结构；其中 `text` 只从 `content.text` 读取非空字符串。飞书富文本/列表消息可能使用不同 `message_type` 或不同 content JSON 结构，本 Story 需要把这类用户可见的文本消息转成稳定 plain text 输入，同时保留附件链路既有行为。

同日后续排障还确认了另一个同属“飞书消息可靠性”的 bug：`aipm` 与 `course-assistant` 的 work-mode 请求已进入 Worker，`cardkit.card.create` / `im.message.create.work_card` 或后续 `cardkit.card.update` 曾返回 `transport_failed`，可见响应是 `volc-dcdn/tengine` 的 HTML `HTTP/1.1 400 Bad Request`，没有飞书 OpenAPI JSON `code/subcode/log_id`。当前日志只记录 operation/outcome/code/subcode/log_id/duration，不记录完整请求体；能从代码推断失败 update 请求体形态为 `PUT /open-apis/cardkit/v1/cards/{card_id}`，body 包含 `card.type=card_json`、序列化后的 `card.data`、`uuid={message_id}-{sequence}` 与 `sequence`。

其中 2026-07-19 16:57 CST 的 `course-assistant` 失败发生在处理图片相关任务过程中：Codex 已生成并脚本验收 `slide_23.png`，最后一条可见进展是准备人工看图；本地 session 没有进入 `view_image` 工具调用，也没有发生飞书图片上传。真正导致 turn 被 abort 的触发点是前序 CardKit update transport failure 把 Worker 内 `presentationFailed` 置位，后续普通 agent message 进入 `OnItem` 时返回 false，runtime 将其解释为展示背压并执行 interrupt，最终整条请求以 `presentation_backpressure` 失败。

## 3. 范围

### 3.1 本期做什么

1. 调研并记录真实飞书富文本列表消息在 SDK 事件中的 `message_type` 和 `content` JSON 结构，至少覆盖项目符号列表和编号列表。
2. 扩展入口标准化逻辑，将支持范围内的富文本结构转换为确定性的 plain text。
3. 富文本转换后的消息沿用现有 receipt、幂等、`messages` 落库、Worker FIFO、work 卡片和 Codex `turn/start` 路径。
4. 对无法支持的富文本节点采取稳定降级文本，而不是静默丢弃整条消息。
5. 增加 ignored 诊断日志的非敏感字段，例如 app、message_type、chat_type、has_content 和 reason，帮助后续区分非文本事件与解析失败。
6. 修复 work-mode 初始卡片创建、interactive message 发送、CardKit update 或 PATCH fallback 失败时的终态语义：展示层失败不得默认中断仍在正常运行的 Codex turn。
7. 引入卡片降级状态：初始可见卡片失败或 unknown 时进入 cardless/degraded presentation，继续 `turn/start`；后续 update 失败时停止或限流后续卡片刷新，但继续收集 Codex final。
8. 最终交付优先走既有文本、文件、图片或安全文本路径；若最终交付也失败，记录为 delivery failure，而不是把 Codex 处理结果改写为模型/图片处理失败。
9. 为飞书发送失败补充可排障但不泄露正文的请求诊断：operation、HTTP/SDK error class、飞书 code/subcode/log_id、是否 HTML 网关错误、payload kind、payload bytes、payload hash、CardKit uuid/sequence。常规日志不得记录完整 card body、用户正文、assistant 正文或凭据。

### 3.2 本期不做什么

- 不实现完整飞书富文本渲染器；目标是可靠 plain text 输入，不保留所有样式。
- 不新增附件类型、表格、投票、卡片、话题群或多媒体消息支持。
- 不新增持久化输出队列、跨进程可恢复 card update cursor 或无限重试机制。
- 不改变 Worker FIFO、App Server Thread/Turn、MySQL 主 schema 或 Langfuse 明文业务数据策略。
- 不把富文本原始 JSON 全量写入日志；诊断日志只保留非敏感结构字段和稳定 reason。
- 不把完整飞书请求/响应 body 写入常规 `slog`；若后续需要本机临时深度抓包，必须是显式人工开关、短窗口、仅本机留存，并在 Story 验收证据里说明清理方式。

## 5. 核心设计决策

| 问题 | 结论 | 原因 | 后果 |
|---|---|---|---|
| 富文本目标形态 | 转换为 plain text。 | Codex 输入当前是文本/附件，不需要保留富文本样式。 | 列表缩进和编号尽量保留语义，样式可丢失。 |
| 支持边界 | 先覆盖飞书聊天框生成的列表富文本。 | 这是已确认用户痛点，范围小且可验收。 | 其他富文本节点可做稳定降级或后续 Story。 |
| 入站失败处理 | 解析失败写稳定 reason 并 ignored；不记录原文。 | 当前静默 ignored 难排障，但日志不能泄露正文。 | 下次能直接判断是未知 type、空 content、解析失败还是不支持节点。 |
| 出站失败处理 | presentation delivery fail-open。 | 飞书/CDN transport failure 是展示层问题，不应中断仍可继续的 Codex turn。 | 用户可能暂时看不到流式卡片，但最终文本/文件/图片交付仍有机会成功。 |
| 背压定义 | 只把本地有界 inbox/candidate 容量耗尽视为 `presentation_backpressure`。 | CardKit API 失败与本地 reader 背压不是同一类故障。 | `OnItem` 不应因为之前的 Feishu update 失败而持续返回 false。 |
| 请求体可观测 | 默认记录 shape/hash/size/sequence，不记录完整 body。 | 需要能解释 Bad Request，同时不把用户内容写入常规日志。 | 可判断 payload 类型、大小、uuid/sequence 与 HTML 网关错误，但默认不能回放完整正文。 |
| 存储契约 | 不新增字段。 | 已有 `user_content` 能保存转换后的 plain text。 | 原始富文本 JSON 不作为业务事实持久化。 |

## 6. 主链路与数据/接口契约

### 6.1 入站富文本识别

1. `Receiver.handleMessage` 从飞书 SDK 事件读取 `message_type`、`chat_type`、`chat_id`、`message_id`、`sender_open_id` 和 `content`。
2. `Normalize` 对 `text/image/file` 保持现有行为。
3. 当 `message_type` 或 `content` 表明它是飞书富文本/列表时，调用独立转换函数输出 plain text。
4. 输出非空时构造 `router.Incoming{Text: ...}`，后续逻辑不分叉。
5. 输出为空或结构不支持时返回 ignored，同时日志记录稳定 reason。

富文本 plain text 最低要求：

- 项目符号列表保留每个条目独立行。
- 编号列表保留条目顺序，可用 `1. `、`2. ` 形式表达。
- 段落、换行和链接文本保留可读语义。
- 不支持的 inline 样式只取可见文本；无法提取文本的节点用稳定占位或跳过，但不能导致整条有文本的消息被丢弃。

### 6.2 出站投递容错

1. Worker 在 `turn/start` 前尝试创建 work card。明确失败或 unknown 时，不得因为缺少初始卡片而直接 fail 当前消息；应记录 `presentation_mode=degraded|cardless` 并继续启动 Codex turn。
2. `UpdateBatchCardZones` 的 CardKit update 失败只影响当次卡片刷新。若 PATCH fallback 也失败或不适用于 CardKit message，Worker 记录稳定 delivery event，并停止继续尝试同一轮流式刷新；不得把 `presentationFailed` 传播成后续 `OnItem=false`。
3. Runtime 的 `OnItem=false` 只保留给本地输出 inbox 容量或字节预算耗尽等真实背压；Feishu API transport/rejected/missing-response 不使用 `presentation_backpressure`。
4. Codex final 到达后，Worker 仍按 mode 执行最终交付：work 优先最终 card update，失败则文本 fallback；附件/工具产生的图片或文件仍按 S05 能力代理发送。最终交付失败时，错误码使用 delivery 语义，例如 `work_card_delivery_failed`、`final_text_delivery_failed`、`image_delivery_failed`，并保留 Codex turn 的真实完成状态。
5. 对 `cardkit.card.create`、`im.message.create.work_card`、`cardkit.card.update`、`im.message.patch`、`im.image.create`、`im.message.create.image` 统一记录发送诊断。HTML `400 Bad Request`、飞书 JSON rejected、SDK transport error、missing response 必须能从日志稳定区分。
6. 对 unknown send 不自动重发同一可见消息，避免重复卡片或重复图片；允许后续不同阶段的确定性 fallback 继续尝试。

阶段级容错矩阵：

| 阶段 | 失败例子 | 本 Story 要求 |
|---|---|---|
| 初始 CardKit entity 创建 | `cardkit.card.create` transport/rejected/HTML 400 | 不启动第二个并发 batch，不把消息标为 `batch_card_create_failed` 终态；进入 cardless work mode，继续 `turn/start`，记录 create failure 诊断。 |
| 初始 work card 消息发送 | `im.message.create.work_card` transport/rejected/unknown | 若发送明确失败，进入 cardless work mode；若发送 unknown，不重发同一初始卡片，继续 Codex turn，并将后续最终交付限定为不会制造重复卡片的 fallback。 |
| 流式 CardKit update | `cardkit.card.update` transport/rejected/HTML 400 | 只关闭本轮流式卡片刷新或进入低频/最终-only 更新；不得让后续 agent item 触发 `OnItem=false`。 |
| PATCH fallback | `im.message.patch` 不支持 CardKit 消息、返回 `230099/200621` 或 transport failed | 记录 fallback 不可用；不得继续盲目 PATCH；转为最终文本/附件交付。 |
| final card update | 最终关闭卡片失败 | 不改写 Codex turn 状态；尝试安全文本 fallback，成功则消息可视为 Codex succeeded + presentation degraded，失败则记录 final delivery failure。 |
| 原生图片/文件发送 | `im.image.create`、`im.message.create.image`、文件上传/发送失败 | 不把图片处理、文件生成或 Codex turn 改写为失败；按 S05 记录 image/file delivery failure，并尽量发送文本说明已生成但交付失败。 |
| 失败提示发送 | 安全文本也发送失败 | 记录最终 delivery failure 和可排障字段；不重放未知可见消息。 |

错误码建议：

- `work_card_create_delivery_failed`：初始 CardKit entity 或 work card 创建/发送明确失败。
- `work_card_create_delivery_unknown`：初始卡片发送结果 unknown，后续必须避免重复可见消息。
- `work_card_update_degraded`：中间 CardKit update/PATCH 失败，已降级但 Codex turn 继续。
- `final_delivery_failed`：Codex 已完成，但最终文本/card 交付失败。
- `image_delivery_failed` / `file_delivery_failed`：本地图片/文件已生成或可用，但飞书上传/发送失败。
- `presentation_backpressure`：仅保留给本地有界 presentation inbox 或字节预算耗尽，不再用于飞书 API/网关失败。

## 9. Definition of Done

- `Normalize` 支持真实飞书列表富文本样本，并保留现有 `text/image/file` 行为。
- ignored 诊断日志能区分主要过滤原因，且不输出原始用户正文或凭据。
- work-mode 卡片 create/update/PATCH 失败不会中断正常 Codex turn，不再把飞书展示层 transport failure 映射为 `presentation_backpressure`。
- 初始卡片发送失败、后续卡片刷新失败、最终文本/图片/文件发送失败具有可区分的稳定错误码和日志字段。
- Feishu Bad Request 排障日志至少能还原请求 shape、payload size/hash、uuid/sequence 和错误类别；常规日志不保存完整请求体、响应体、用户正文或凭据。
- `go test ./internal/feishu ./internal/router -count=1` 通过。
- `go test ./internal/worker ./internal/codexapp ./internal/feishu -count=1` 覆盖输出投递容错和回归用例。
- 涉及运行态后按项目规则执行 `./bot_controller.sh build`、`./bot_controller.sh restart`、`/healthz` 和 `/readyz`。
- 完成一条真实飞书列表富文本 L4 校验和一条 CardKit/发送失败容错 L4 或受控故障注入校验，记录脱敏证据。

## 10. 风险、残留项与后续 Story

- 飞书富文本 content 结构可能随客户端或平台版本变化；实现时应优先基于真实样本和官方结构，同时保持 unknown-node 降级。
- 若飞书把某些富文本作为非 `P2MessageReceiveV1` 或非普通消息事件投递，本 Story 只记录 evidence，不扩大到新事件订阅。
- 表格、代码块、富媒体混排和 topic_group 支持均不在本期。
- 飞书/CDN HTML 400 的真实根因可能在 SDK、网络、HTTP 网关或飞书平台侧；本 Story 不能保证外部平台不失败，只保证本地编排器不把展示层失败误判为 Codex/图片处理失败。
- unknown send 不自动重放意味着极端情况下用户可能仍看不到某条中间卡片；验收重点是继续处理、最终降级交付和可排障证据。
