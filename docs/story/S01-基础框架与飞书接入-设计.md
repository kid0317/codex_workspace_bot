# Story 1：基础框架、配置、MySQL 与飞书固定回显

> **状态**: Delivered  
> **日期**: 2026-07-10  
> **对应概设**: [概要设计 v3](../02-redesign-high-level.md)
> **依赖**: Docker MySQL、测试飞书自建应用（长连接、事件订阅和消息权限）、本机 3306 端口；Codex 登录为后续 Story 的非阻塞依赖

## 1. 一句话目标

让本地操作者可配置多个飞书应用并验证 text 收发和可追溯持久化，为后续 Codex 编排提供已验证的接入底座。

## 2. 背景

当前仓库仅有设计文档。Story 1 要交付一个可本机常驻运行的 Go 服务：从 MySQL 读取已启用飞书应用，以应用凭证建立 WebSocket 事件连接；收到文本单聊或群聊消息时，持久化一轮 Message，并按应用和聊天渠道信息发送固定文本回复。

该 Story 的价值是验证最早、最外层的真实边界：多飞书应用凭证、长连接事件、发送消息、MySQL 持久化、配置加载和排障日志。它不会接入真实 Codex 模型，因此任何通过本 Story 的验证都不得被描述为 App Server 或模型链路已验收。

## 3. 范围

### P0

1. 建立 Go module、`cmd/server`、本地 `cmd/appctl` 和边界清晰的 `config`、`storage`、`feishu`、`router`、`output` 包。
2. 以版本化迁移创建 `apps`、`chat_groups`、`messages` 三表，完成各自必要 CRUD / upsert / 状态更新接口；`appctl` 提供 App 的 create/list/update/enable/disable/delete，作为一期唯一的人工配置入口。
3. 每轮创建 UUID `message.id` 和 32 位小写十六进制 `trace_id`；以 App + 飞书 event ID 为 seed 生成 Langfuse/W3C 兼容 Trace ID，并按 ChatGroup 范围对 event/message ID 幂等。
4. 读取 YAML 与环境变量，验证配置；从 DB 加载 enabled 应用并对每个应用启动一个飞书 WebSocket 接收器。
5. 接收 `im.message.receive_v1` 的 `text` 消息，处理 `p2p` 与 `group`；创建或取得 ChatGroup，记录 Message，发送固定回复，再回写最终状态与出站 ID。
6. 提供 `docker-compose.yml`、`.env.example` 和 `config.yaml.template`；MySQL 数据 bind mount 在主机 `runtime/mysql-data`，通过 `restart: unless-stopped` 恢复。
7. 使用 JSON `slog`，不记录 Secret、DSN 密码、认证头或消息正文；服务自身写入 `logs/server.log` 与 `logs/server.log.wf`，按小时切分、按日目录归档。

### 非目标

- 不调用 `codex app-server`，不创建/恢复 Thread，也不实现 `/new`。
- 不实现真正的 Worker 池、并发调度、进程重启后的进行中任务恢复。
- 不处理图片、文件、富文本、话题群、卡片交互或审批。
- 不发送 Langfuse 事件；只保证 `trace_id` 可在下一 Story 复用。
- 不构建后台管理 UI、应用 CRUD HTTP API 或加密 Secret。

## 5. 核心设计决策

| 方案 | 结论 |
|---|---|
| 所有应用配置放 YAML | 不采用：与需要可持久化管理的 App 表冲突，且存在双源风险。 |
| YAML 作为进程配置、App 表为应用配置唯一来源 | **采用**：全局运行参数可版本化，应用凭证与策略能由 DB 管理。 |
| 每个角色一条 Message 行 | 不采用：无法直接表达“一个请求及最终结果”的审计单元和一个 Langfuse trace。 |
| 一轮一条 Message 行 | **采用**：`user_content` 与 `assistant_content` 同行，`trace_id` 一轮一个。 |
| Trace ID 格式 | **采用**：由 App + 飞书 event ID 确定性导出的 32 位小写十六进制 | 与 Langfuse/W3C Trace Context 对齐，重投保持同一关联 ID |
| 单 App receiver 故障 | **采用**：记录 `reconnecting/fatal`，其他 App 继续工作 | 多 App 本地隔离；不把短暂外部连接问题升级为进程失败 |
| Worker 与队列 | **延期**：仅在 HLD 固化契约，S01 不实现 | 本 Story 先验证持久化与飞书边界，下一 Story 再引入串行调度 |

## 6. 设计

### 6.1 包边界

```text
cmd/server              组装依赖、信号关闭、健康检查
cmd/appctl              本地应用配置 CRUD；不启动 HTTP 管理面
internal/config         YAML + 环境变量加载、默认值、校验
internal/storage        MySQL 连接、迁移、App/ChatGroup/Message Repository
internal/feishu         SDK 适配、每 App WebSocket receiver、发送 text
internal/router         入站规范化、幂等、ChatGroup/Message 生命周期、固定回复
internal/output         固定回复格式（未来替换为卡片/分段输出）
```

接口定义在消费方：`router` 消费 `AppRepository`、`ChatGroupRepository`、`MessageRepository`、`FeishuSender`。生产 MySQL/飞书适配器保持小；测试提供 fake，不为内部局部逻辑抽象接口。

### 6.2 配置

实现时提交 `config.yaml.template` 和 `.env.example`，实际 `config.yaml`、`.env`、`runtime/` 加入 `.gitignore`。`appctl` 通过同一配置连接 MySQL，接收 App 名称、飞书凭证、CWD、模式、模型、effort 及启用状态；不把凭证回显到终端。App Server 使用全局 full access，不做每 App sandbox 配置。配置字段和校验规则以概设第 6 节为准。

启动失败条件：无法加载配置、DB 无法连接/迁移失败、无应用、某启用 App 的 CWD 不存在、重复 App ID 或非法枚举。禁用 App 不创建连接；单个 App receiver 连接失败只进入 `reconnecting/fatal` 状态并记录日志，不退出其他 App 的服务。

### 6.3 Docker MySQL

Compose 服务名 `mysql`，采用固定 MySQL 8.4 镜像、`127.0.0.1:3306:3306`、健康检查、`restart: unless-stopped` 和 `./runtime/mysql-data:/var/lib/mysql`。首次启动用 `.env` 中的 root 密码、应用 DB 名、应用用户及密码初始化；Go 服务以最小权限应用用户连接，不使用 root。

验收前检查 Docker 已启动、挂载目录实际出现 InnoDB 文件、容器 health 为 healthy，且 `docker compose restart mysql` 后数据仍在。主机重启自动恢复由已启用的 Docker systemd 服务和 restart policy 共同保证；实现后须实际验证容器 restart policy。

### 6.4 数据操作与状态机

```text
event arrived
  -> INSERT message(status=received, trace_id)
  -> duplicate key => stop and do not reply
  -> processing
  -> send fixed text
  -> succeeded (store bot message ID, content, completed_at, duration)
       or failed (store stable error code, safe error message, completed_at)
```

ChatGroup 使用 `(app_id, chat_type, chat_id)` 原子 upsert，因此同一群中的不同 App 对应不同 ChatGroup。Message 创建、ChatGroup touch 和事件幂等必须在一个短事务内完成；不得持有 DB 事务等待飞书 API。飞书发送失败只更新该行失败，不重试、不重复创建用户轮次。

固定回复不得泄漏 Secret、CWD 或原始消息；建议内容：`已收到：应用=<name>，渠道=<chat_type>/<chat_id>，trace_id=<trace_id>`。群聊与单聊分别按 SDK contract 选择接收 ID。

### 6.5 飞书接入

每个 enabled App 用其 `feishu_app_id` 与 `feishu_app_secret` 构造一个 SDK WebSocket Client，注册 `OnP2MessageReceiveV1`。Receiver 必须验证事件 `header.app_id` 等于该 client 的 `feishu_app_id`，且 `header.event_id` 非空。Receiver 状态记录为 `connecting`、`connected`、`reconnecting`、`fatal` 或 `stopped`。一期仅将 `message_type=text`、`chat_type=p2p|group` 交给 Router：

- p2p：ChatGroup 以事件 `chat_id` 定位；回复 `sender.sender_id.open_id`，`receive_id_type=open_id`。
- group：ChatGroup 以事件 `chat_id` 定位；回复该 `chat_id`，`receive_id_type=chat_id`。
- 忽略项写结构化日志且不发送：消息/身份字段缺失、非 text、`topic_group`、未知类型、header 不匹配或重复事件。

开发者后台需要把该应用配置为长连接，并订阅 `im.message.receive_v1`，授予接收单聊/群聊消息及发送消息所需权限。长连接只支持企业自建应用；SDK 会负责长连接鉴权和加密传输。

### 6.6 日志与 Trace

每一轮从入站时产生 Langfuse/W3C 兼容的 32 hex `trace_id`，贯穿 Router、Storage、Feishu sender。至少有：`server_started`、`mysql_connected`、`migration_applied`、`feishu_connected`、`feishu_reconnecting`、`message_deduplicated`、`message_completed`、`message_failed`。日志字段中 `app_id` 是本地 UUID，`channel_key` 可记录，`sender_open_id` 不记录，正文不记录。

普通服务事件写 JSON Lines `logs/server.log`，工作流事件预留写入 `logs/server.log.wf`。`logging.level` 仅允许 `debug|info|error`，默认 `info`；`logging.dir` 默认 `logs`。服务启动、每分钟后台检查和跨小时切分均会将 current 文件重命名为 `server-YYYYMMDDHH.log`（WF 同名加 `.wf`），再创建新的 current 文件。所有早于今天且仍位于日志根目录的切分文件，移入 `logs/YYYYMMDD/`；服务不依赖系统 cron/logrotate，也不在一期删除或压缩归档。

### 6.7 文件日志后台任务：实施设计与步骤

日志文件只由服务管理，目录契约如下：

```text
logs/
  server.log
  server.log.wf
  20260711/
    server-2026071100.log
    server-2026071100.log.wf
```

- `server.log` 记录普通服务事件；`server.log.wf` 为后续 Worker/App Server 工作流事件预留。两者均为 JSON Lines。
- `logging.level` 只允许 `debug|info|error`，默认 `info`；`logging.dir` 默认 `logs`。非法级别或空目录使启动失败。
- 服务启动时创建两个 current 文件；每分钟后台检查时间，进入新小时后关闭并重命名上一小时的 current 文件，再创建新的 current 文件。
- 同一后台检查会补偿归档：所有日期早于今天、仍在日志根目录的已切分文件，移动到 `logs/YYYYMMDD/`；current 文件不移动。服务在零点不运行时，下次启动仍会完成归档。
- 服务关闭时取消后台任务并同步关闭 Writer；不依赖 cron/logrotate，不压缩、不删除归档。

**实现步骤（TDD）**：

1. 扩展配置测试与实现：断言日志目录默认值、三个合法等级和非法输入拒绝。
2. 新建 `internal/logging`：先测试双 current 文件创建、普通/WF Logger 分流和等级过滤；再实现双 JSON `slog.Handler`。
3. 以可注入时钟测试跨小时切分和跨日目录归档；再实现后台 ticker、`Check(now)`、严格文件名匹配和启动补偿。
4. 在 `cmd/server` 创建并启动 Manager，把普通 Logger 设为默认、保留 WF Logger；context 结束时关闭 Manager。
5. 更新 README，并运行 `gofmt`、`go vet ./...`、`go test ./...`、`go test -race ./...`；本机验证两个 current 文件、切分和归档目录。

## 9. 最终本地集成校验

### S01-LI-01：真实飞书 text 收发与持久化闭环

**目标**：证明本机服务能以配置的真实飞书 App 接收 p2p/group text，回显正确的 App/ChatGroup 信息，并把一轮消息可追溯地落入 MySQL。

**前置**：

1. Docker 服务运行，`docker compose up -d mysql` 后 MySQL health 为 healthy，`runtime/mysql-data` 已出现持久化数据文件。
2. 已复制并填写本地 `.env`、`config.yaml`；`CODEX_WORKSPACE_BOT_DB_PASSWORD` 可用，3306 未被其他服务占用。
3. 通过 `appctl` 写入一个 enabled 测试 App，CWD 为存在的绝对路径；list 输出不含 App Secret。
4. 飞书开发者后台已为该自建应用启用长连接，订阅 `im.message.receive_v1`，授予接收单聊/群聊消息和发送消息权限；Bot 已加入一个测试群。
5. 终端 A 启动服务并保留 JSON 日志；终端 B 可连接 MySQL 查询 `apps`、`chat_groups`、`messages`。

**操作与预期**：

| 步骤 | 操作 | 预期与要保存的证据 |
|---|---|---|
| 1 | 启动服务 | 日志有 `mysql_connected`、`migration_applied`、测试 App 的 `feishu_connected`；记录启动时间。 |
| 2 | 用个人飞书给 Bot 发一条独特 p2p text，例如 `S01-P2P-<时间戳>` | 收到固定回复，包含 App 名称、`p2p`、Chat ID 和 32-hex `trace_id`；保存回复截图与 trace ID。 |
| 3 | 在测试群发送 `S01-GROUP-<时间戳>` | 群内收到固定回复，包含同一 App 名称、`group`、Chat ID 和新的 trace ID；保存截图。 |
| 4 | 查询 MySQL | 每条输入各有一个 ChatGroup（p2p/group）和一条 `messages` 记录；`status=succeeded`、入/出站 message ID、`assistant_content`、`completed_at`、`duration_ms` 与 trace ID 完整。 |
| 5 | 检查服务日志 | 每个 trace ID 可找到 `message_completed`；日志不包含 App Secret、DB 密码、认证头或用户正文。 |
| 6 | 重启 MySQL 容器并重新查询 | MySQL health 恢复，步骤 4 的记录仍存在；保存 `docker compose ps` 与查询结果。 |

**失败处理**：先按顺序检查 Docker/MySQL health、服务中 `feishu_connected/reconnecting/fatal` 状态、飞书后台事件订阅和权限、测试群 Bot 成员关系，再检查对应 trace ID 的本地日志和 Message 状态。失败必须记录发生时间、输入标识、trace ID、Feishu message ID、日志错误码和数据库状态；本地 fake 通过不能替代该用例。
