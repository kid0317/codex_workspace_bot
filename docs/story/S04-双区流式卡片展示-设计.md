# S04：双区流式卡片展示

> **状态**：Delivered（2026-07-13）
> **关联概设**：[HLD v4.2](../02-redesign-high-level.md) §4、§5.5、§6
> **依赖**：S03 已 Delivered；测试飞书 App 的机器人、`im:message`、`im:message:send_as_bot`、`cardkit:card:write` 权限；支持 Card JSON 2.0 的飞书客户端（7.20+）。

## 1. 一句话目标

让使用 work mode 的用户在**同一张飞书卡片**中持续看到 Codex 已完成的中间进展，并在收到权威最终答复后看到清晰、完整的正文；让 companion mode 不展示任何中间状态或占位卡，只在 Turn 成功结束后把最终答复按旧 CC Workspace Bot 的多条文本消息语义送达。

## 2. 背景

S03 已验证真实 App Server、同一张飞书 interactive card PATCH、完整原始 event 时间线和 `item_id` 索引。修复后的真实 L4 样本包含 5 条 `item/completed` 的 `agentMessage`：4 条 `phase=commentary` 和 1 条 `phase=final_answer`；同时混有 reasoning、commandExecution、fileChange、userMessage、webSearch 等不应显示给用户的 Item。

因此 S04 不使用高频 `item/agentMessage/delta` 直接渲染。唯一的用户展示内容源是已完成的 `agentMessage` Item：在 work mode 中仅 `phase=commentary` 表示可读进展，`phase=final_answer` 表示正文；在 companion mode 中只有 `phase=final_answer` 可成为候选答复，且必须等成功终态后才出站。缺失或未知 phase 不展示。该规则来自真实 payload，而不是协议猜测。

飞书官方 CardKit JSON 2.0 支持卡片实体；当前锁定 Go SDK 已包含 CardKit v1 客户端。真实 L4 已验证同一实体的全量 `Card.Update(card_json)` 可稳定更新双区，因此它是本 Story 的正式主路径。S02 的 `Im.Message.Patch` 仅是单次 CardKit 更新失败时的同 message 兼容降级，不是主体验，也不会永久关闭后续 CardKit 尝试。

## 3. 范围

### 3.1 本期做什么

1. 为 work mode 创建 JSON 2.0 CardKit card entity 并仅发送一次，以同一张 card 的 `card_id` 全量更新双区 `card_json`。
2. 建立按 active Batch/Thread/Turn 隔离、由 channel Worker 独占的 `CardProjection`，保存进展、正文、已见 `item.id`、CardKit sequence 和终态。
3. 只解析已路由到该 Turn 的 `item/completed`：`item.type=agentMessage`、非空 `text` 且 phase 在显式白名单内；`commentary` 追加进展，`final_answer` 写正文。
4. 按固定节流更新进展区，并在 final/terminal 时立即刷新、关闭 CardKit `streaming_mode`，保留稳定卡片。
5. 当 CardKit 权限、实体创建或某次全量实体更新不可用时，仅对该次更新以同一 `message_id` 的整卡 PATCH 保持双区内容；最终 PATCH 失败沿用 S02 的一次 text fallback 和 MySQL 合法终态。
6. 增加事件 mapper、projection 状态机、CardKit adapter、Worker 串行和 fake Feishu/App Server 测试，并用真实飞书 L4 验证同卡流式更新。
7. 为 companion mode 增加终态 final-only 交付：不创建占位卡、不发送进展；仅在成功终态后按旧 CC Workspace Bot 的 `[[SEND]]` 分段和打字延迟，顺序发送多条 plain-text 消息。

### 3.2 本期不做什么

- 不展示 `item/agentMessage/delta`、reasoning、commandExecution、fileChange、userMessage、webSearch、token/rate-limit、raw JSON 或 debug 日志。
- 不做取消、重试、审批等卡片按钮；飞书流式模式期间不能直接处理卡片交互，既有/后续命令 Story 另行定义 UX。
- companion 不使用富卡片、CardKit、inline PATCH 或正文“思考中…”占位；它的范围仅限终态 final-only 的纯文本多消息交付。
- 不迁移旧 CC Workspace Bot 的 `FINAL_REPLY.md` / Claude Stop-hook persona 过滤协议；若后续仍需要相同的角色输出质量，单开 Codex-native output-policy Story。
- 不恢复 bot 整体重启前的活跃 CardProjection，也不重放被 S03 中断的 Turn；流式模式会由飞书自动在 10 分钟后关闭。
- 不在本期实现可展开的工具轨迹、引用、用量面板、多语言、卡片搭建工具模板或 Langfuse 投影。

## 5. 核心设计决策

| 问题 | 结论 | 原因 | 后果 |
|---|---|---|---|
| 哪些 App Server 内容可见 | 仅 `item/completed` 的 `item.type=agentMessage`、text 非空，且 phase 为 `commentary` 或 `final_answer` | 真实样本支持这两个 phase；其余 Item、空/未知 phase 一律不展示。 | mapper fail-closed，未知 phase 只写稳定诊断字段。 |
| 中间与最终如何区分 | `phase=commentary` 只写进展；`phase=final_answer` 只写正文 | 用户已裁定；不从文字猜测意图。 | 无 final 不拿中间文本冒充答案。 |
| 模式分流 | work mode 立即创建并更新双区卡；companion mode 不创建卡、不展示 commentary，只暂存 `final_answer`，等待成功终态后发送 | 任务型应用需要过程可见性；陪伴型应用只应给用户完整答复。 | 同一事件流有不同 output sink；companion 的任何飞书出站都不得早于 Terminal。 |
| Markdown 安全边界 | 展示 mapper 后必须经过 presentation sanitizer；标准 Markdown 可保留，所有 `<`、`>`、`&` 及飞书专有标签转为不可执行字面字符 | agentMessage 仍可能受提示注入影响；飞书 Markdown 支持标签/提及语法。 | 任何 `<at>`、`<link>`、HTML/飞书标签均不得出现在出站卡片请求中。 |
| 卡片结构 | 无 header、无进展标题；顶端以灰色斜体富文本展示进展，其后固定分隔线，再展示正文 | 依靠排版而非状态标签区分过程和答复，减少对正文的干扰。 | 使用 JSON 2.0 源码而不是 Card Builder。 |
| 主更新通道 | CardKit card entity + 同一 `card_id` 的全量 `Card.Update(card_json)` | 真实 SDK/L4 已证实该路径可正确更新双区，避免组件 Content API 的参数与展示歧义。 | 每个 Projection 保存 card ID、递增 sequence 与关闭状态。 |
| 兼容降级 | CardKit 不可用时，复用同一 `message_id` 的 `Im.Message.Patch` 全卡更新 | S02 已真实验证，仍保证双区内容而不新建完成卡。 | 降级没有飞书原生打字机效果，但不影响用户语义。 |
| 并发与顺序 | Worker 是 Projection 和卡片 sequence 的唯一所有者；单一 flush loop 串行执行 | CardKit 要求同一卡 sequence 严格递增；同 channel 已 FIFO。 | Runtime 不直接写 Feishu；跨 channel 各自独立。 |
| 出站大小与频控 | 每个实际序列化后的 CardKit/inline card 请求限制为 28 KiB；CardKit 限速 10/s、PATCH 限速 5/s，最终操作只提升优先级、不突破限速 | 飞书 Card/消息最大 30KB，JSON 转义会放大文本；final/settings/retry 也占用同一限速。 | 进展保留最新条目并显示“较早进展已省略”；超卡片预算的 final 走受 150KB 文本上限约束的确定性分段 fallback。 |
| Terminal 与命令竞态 | 每个 attempt 只有一个 `TerminalArbiter`；companion 在 attempt 创建时同时创建 `DeliverySlot`，控制面可在线性化点前阻止成功 Terminal 后的首段发送 | 同一 channel 的 `/cancel`、`/new` 必须能停止成功 Terminal 后的 companion delivery，且不得让旧 Batch 与新 Batch 交叉。 | `DeliverySlot{cancel_requested,published,done}` 与 `BeginDelivery` 共用 Worker mutex；命令置 latch 并等待 done。 |
| companion 可见发送与收尾 | 每段外发至多尝试一次；MySQL/trace 收尾可重试但绝不重发已外发段 | 飞书成功后 DB 失败不能以“重跑 Batch”恢复；网络未知结果也不能安全重发。 | 发送结果区分 `sent/rejected/unknown/cancelled`，未知结果停止余段，DB retry 只执行 transaction。 |
| 展示背压 | pre-bind 与 post-bind 均有事件/字节上限；满时展示 attempt 确定性失败并 interrupt，不引入 spill queue | 有界、reader 不阻塞、展示 Item 不丢三者不能同时成立。 | 原始 S03 本地 event 仍保留；超限 Item 不进入 output state，用户收到安全失败终态。 |
| batch 交付关联 | `batch_id` 是 companion 交付的主关联键，记录全部 `source_trace_ids` | 一个 Batch 可合并多条用户 Message，不能任取其中一个 trace 当唯一 owner。 | 第一条可见发送前，所有 source Message 持久化同一 `companion_delivery_batch_id` 和 `delivery_stage=companion_delivery_started`；每个 segment trace 记录 batch、source traces、turn、index 和 digest。 |
| 多 final 选择 | 同 `item.id` 去重；不同 final Item 在 Terminal 前按到达序覆盖，latest non-empty final wins | 真实样本当前仅一个 final，但协议/重投不能假定永久唯一。 | Terminal 后拒绝 late Item，最终只送一次最后一个合格 final。 |

## 6. 主链路与数据/接口契约

### 6.1 卡片信息架构（UI 设计结论）

```text
┌────────────────────────────────────────────┐
│ 正在检查当前实现…                          │
│ 正在定位卡片 API…                          │  ← progress_text（灰色斜体）
│ 正在整理方案…                              │
├────────────────────────────────────────────┤
│ 正文                                       │
│ 思考中…                                    │  ← final_text
└────────────────────────────────────────────┘
```

终态只改变正文和流式开关；进展保留。卡片不用 header、状态标签、按钮、头像、时间线图或工具详情。`final_text`、`progress_text` 是全卡唯一、字母开头且不超过 20 字符的 `element_id`。进展通过 Markdown 斜体和组件 `font_color=grey` 区分，模型文字在此前已 sanitizer，不能注入样式标签。

初始 CardKit JSON 的必要结构如下（省略样式细节）：

```json
{
  "schema": "2.0",
  "config": {
    "streaming_mode": true,
    "update_multi": true
  },
  "body": {"elements": [
    {"tag": "markdown", "element_id": "progress_text", "font_color": "grey", "content": "*等待 Codex 进展…*"},
    {"tag": "hr"},
    {"tag": "markdown", "element_id": "final_text", "content": "*思考中…*"}
  ]}
}
```

### 6.2 Work-mode 展示 mapper（唯一允许名单）

| 输入条件（已验证属于当前 Thread+Turn） | Projection 动作 | 飞书动作 |
|---|---|---|
| `item/completed`，`item.type!=agentMessage` | 忽略 | 无 |
| agentMessage 但 text 空、item.id 空、phase 缺失/未知或已见 item.id | 忽略并记录稳定诊断字段 | 无 |
| agentMessage，`phase=commentary` | 以 item.id 去重，按到达顺序追加经 sanitizer 处理后的 text；相邻条目用空行分隔 | 标记进展脏，由 flush 合并 |
| agentMessage，`phase=final_answer` | 覆盖经 sanitizer 处理后的 `final_text`，锁定 final item id | 立即更新正文；不写进展 |
| `turn/completed.status=completed` 且有 final | flush 进展、关闭流式、摘要改“已完成” | 终态同卡更新 |
| completed 但无 final | flush 进展，正文写“本轮完成，但未收到可展示的最终答复。”，关闭流式 | 明确异常终态 |
| failed/interrupted/timeout/runtime exit | 停止接受 event，正文写现有确定性安全失败文案，关闭流式 | 同卡终态；失败时一次 text fallback |

`item/agentMessage/delta` 仍能重置 S03 的 idle timer，但不进入 mapper、Projection 或飞书调用。sanitizer 在 mapper 后、Projection 前执行；其输入/输出不写 MySQL、Langfuse 或普通日志。

### 6.3 Companion mode：终态 final-only 多消息交付

companion Worker 在 `turn/start` 前**不**调用任何飞书发送接口：没有 CardKit entity、没有 interactive card、没有“思考中…”文本，也不为 `commentary` 或其它 Item 创建可见消息。它仍接收已绑定 Turn 的事件以维持 S03 路由、idle timeout、终态和 drain 语义，但展示层仅保留 latest non-empty、经 presentation sanitizer 处理的 `item/completed.agentMessage.phase=final_answer` 文本作为 `pending_final_text`。同 `item.id` 只接受一次；不同 final Item 在 Terminal 前按 App Server 到达顺序覆盖（latest non-empty final wins），Terminal 后一律拒绝。`commentary`、delta、未知 phase 和其它 Item 一律不出站。

只有 `turn/completed.status=completed` 且 `pending_final_text` 非空时，Worker 才先调用 `CompanionDelimiterLexer`，再将得到的语义段交给 `CompanionSegmenter`。**usable final** 的定义是该链路至少产出一个非空可发送段；例如 `[[SEND]][[SEND]]` 虽有原始 text，但分段结果为零，不是 usable final。该实现必须兼容 `/root/cc_workspace_bot/internal/session/segment.go` 的已验证用户语义，并在其前补上对模型不稳定标记的兼容：

1. `[[SEND]]` 是显式语义分段符；按出现顺序切分、trim、丢弃首尾/连续分隔产生的空段，标记本身绝不发送。
2. 没有分隔符时，先按双换行分段；只有全文仍是一段且超过 80 rune 时才按句末标点分段；随后去空段、合并短段、按 rune 边界硬切。若此 fallback 会得到超过 3 段，则退回为原文单段，避免把一条完整答复机械拆碎。
3. 有显式 `[[SEND]]`，或未触发“超过 3 段退回原文”的 fallback 时，每段默认不超过 80 rune；短于 2 rune 的相邻段在不超过上限时合并。退回原文单段可超过 80 rune，这是旧实现为避免过度碎片化的特例。该长度与 `streaming.companion_segment_delay_ms=400`、每字阅读/输入速度、首条 300–1500ms、后续 600–2000ms（含抖动）的打字节奏共同构成旧 companion 的体验基线，而不是 work mode 的卡片节流。
4. 每段按序使用普通飞书 text 消息发送；前一段发送（及其延迟）未完成前不得发送后一段。发送使用 Worker/batch-owned 的 `DeliveryHandle{batch_id,cancel,done}`，而非成功 Terminal 后可能已结束的 turn context。`BeginDelivery` 是唯一发布 Handle 的线性化操作：它先在 `DeliverySlot` mutex 内确认“successful Terminal、drain 已完成、未 `cancel_requested`”，将 slot 置为 `starting`；再以单一 MySQL transaction 为所有 Batch source Message 条件写入相同、不可变的 `companion_delivery_batch_id` 和 `delivery_stage=companion_delivery_started`；最后重新取得同一 mutex，只有仍未被控制面置 latch 才发布 Handle 并开始首段 delay。任何 `/cancel`、`/new`、Worker stop 或 shutdown 在 slot 从 attempt 创建到 `Drained` 的任意时刻都能置 `cancel_requested`：若 Handle 未发布，`BeginDelivery` 不得调用 SendText；若已发布，则取消其 context 并等待 `done`。控制面先取得该 mutex 时，`SendText=0`；`BeginDelivery` 先发布时，控制面只能取消尚未完成的 delay/API/retry，已得到 Feishu response 的段不撤回。单段 5 秒请求超时；明确 429 只对该段退避 500ms 并重试一次；明确 rejected 错误记录后继续后续段。timeout、连接断开或“服务端可能已接收”的结果分类为 `unknown`：不重试该段、停止余段以避免乱序/重复，交付摘要为 `companion_segment_delivery_unknown`。`streaming.companion_segment_delay_ms` 仅覆盖旧 `SegmentOptions.BaseDelay`，默认 400ms、启动时校验为 `0 < value <= 2000ms`；其余 delay/RNG 常量保持旧默认且不热更新，测试必须注入 fake clock/seeded RNG。
5. 每个 API result 后，在启动下一段前写一条本机 workflow JSONL `event=companion_segment_delivery`：`batch_id,source_trace_ids,thread_id,turn_id,segment_index,text_sha256,result(sent|rejected|unknown|cancelled),reason|null,message_id|null,retry_count,at`。`text_sha256` 是 UTF-8 segment 的小写 SHA-256；不得写正文、delimiter 或 token。首次 429 写 `result=rejected,reason=rate_limited,retry_count=0`，500ms 后的同段重试写 `retry_count=1`；第二次仍为 429 是明确 rejected，继续后续段。`reason` 只允许稳定枚举，绝不记录 API 原文。该本地 workflow log 是必达交付证据，Langfuse 仅 fail-open 复制无正文 metadata。写入失败时停止余段、标记 `companion_delivery_trace_incomplete`，不得静默继续。
6. `messages.assistant_content` 必须使用 Lexer 的 `storage_text`，而非对原始 final 再做精确 `strings.ReplaceAll("[[SEND]]", "\\n")`：所有**已识别**的兼容 delimiter span 统一替换为换行（独立行的 quote/list/backtick wrapper 一并去除），code/inline-code 的字面 marker 保持原样；转义 marker 也保持字面，但依第 4 条只移除用于转义的一枚反斜杠。发送循环将每段 API result 追加到 attempt-local immutable delivery ledger；`CompleteBatch` 只接收该 ledger 导出的 `CompanionDeliverySummary{batch_id,source_trace_ids,first_success_message_id,attempted,sent,rejected,unknown,cancelled,error_code}`。它在一个 MySQL transaction 内将 Batch **全部**仍为 `processing AND companion_delivery_batch_id=? AND delivery_stage=companion_delivery_started` 的 Message 条件更新为同一 final content、首成功 ID、duration、摘要 error code、completed_at，并清除 `delivery_stage`；任一行 RowsAffected 不为 1 或任一 SQL 错误都 rollback。marker 写入后的非成功路径必须改用同样 batch/stage 条件的 `FailCompanionDelivery(ctx,batchID,errorCode,safeContent,duration)`：一个 transaction 把全部 source Message 迁移为 `failed`、写 `completed_at` 并清除 stage；控制在 Handle 发布前取消写 `companion_delivery_cancelled`，已发布后的 cancel/stop、trace writer failure 和其它本 generation delivery failure 分别写稳定 error code。两个 finalize API 的 transient DB 错误都只重试自身 transaction，绝不回到 SendText；只有 fail-finalize 最终失败且 generation 随后退出的 marker 行才留给启动 reconciliation 标记 abandoned。最终 DB 失败写本机 `companion_delivery_finalize_failed` 证据。`status=succeeded` **只**表示 Turn/最终内容成功完成，不表示每个飞书分段均已送达；不新增 segment table 或 JSON 字段，但本 Story 增加上述两个最小 Message 列，不保存 segment cursor/已发送段。

**用户裁定（2026-07-12）**：companion 不设 `max_segments`、总字节或总 delivery duration 限制；保持模型给出的全部分段，直到正常发送完毕或被 `/cancel`、`/new`、Worker stop 中断。同 channel 因此在 delivery 完成/中断前保持串行占有，不能用“超限合并/截断”提前释放。

**崩溃/重启语义（用户裁定 A）**：每个 live bot generation 对 companion delivery 只做一次可见发送尝试，绝不为恢复而重发任何已计划/已发送段。进程在 delivery 中退出后，新进程不恢复该 Batch、不继续余段；启动 reconciliation **只**选择 `status=processing AND delivery_stage=companion_delivery_started AND companion_delivery_batch_id IS NOT NULL` 的行，按持久化 batch ID 分组，并条件迁移同组全部 source Message 为 `failed`、`error_code=companion_delivery_abandoned`、清除 `delivery_stage`。其 abandoned trace 必须复用原 batch ID 和该组完整 source trace IDs，并记录“可能部分可见”的无正文证据；不得调用 SendText。work mode、尚未进入 delivery 的 companion Turn 和无 marker 的普通 processing 行继续走既有 runtime-exit 收尾，绝不得被误标 abandoned。该选择不引入 segment ledger/outbox，也不承诺完整送达。

若成功终态没有 usable final（包括缺少 final 或 marker-only 的零段结果），companion 不调用 normal final 的 `CompanionDeliverySummary`，而只发送一条确定性安全文案“本轮完成，但未收到可展示的最终答复。”；其 Message 写安全文案、该安全消息 ID，并写 `error_code=companion_final_empty`。failed/interrupted/timeout/runtime exit 则只发送一条既有 companion 失败文案，绝不把先前暂存的 final 当作成功答复。上述分支同样没有卡片。

#### `CompanionDelimiterLexer`：模型输出兼容规则

不能把整段文本直接做一次宽松 `strings.Split`：模型既可能把控制符写得不规范，也可能在回答中解释这个符号。Lexer 按原文的 code-fence/inline-code/转义边界扫描，产出 `{segmenter_input, storage_text, delimiter_token, rule_counts}`；普通正文的字符、换行和 Markdown 不被全局 Unicode 归一化。

1. **候选规范化仅作用于候选标记。**先在候选范围删除零宽字符（`U+200B/U+200C/U+200D/U+FEFF`），将全角/方头括号 `［］【】〔〕` 折叠为 `[]`，并作 NFKC；原始正文仍原样交给后续 sanitizer/Segmenter。
2. **双括号兼容（可内联）。**规范化后的 Go RE2 为 `(?i)\[\s*\[\s*s\s*e\s*n\s*d\s*\]\s*\]`；因此 `[[SEND]]`、`[[ send ]]`、`［［s E N D］］` 和 `【【SEND】】` 都是 delimiter。精确旧写法仍保持可内联分段的兼容。
3. **单括号容错（只允许独立控制行）。**规范化后的候选 Go RE2 为 `(?i)^[\t ]*(>\s*)?([-*+]\s*)?\[\s*s\s*e\s*n\s*d\s*\][\t ]*$`；它接受 `[SEND]` 及其 quote/list 的整行变体。若去掉 quote/list 后剩余文本由反引号包裹，Lexer 先手工验证 opening/closing 的反引号数**相等**且为 1、2 或 3，再识别内层 marker；不配对的 `` `[SEND]``` 或 `` ```[SEND]` `` 是正文。双括号仍按第 2 条识别；任何正文中的普通 `SEND` 或 `[SEND]` 词语都不拆开。
4. **保护正文和反斜杠奇偶。**fenced code block（反引号或 `~`，closing 必须与 opening 字符相同且长度不少于 opener）内的候选、非整行 inline-code candidate 都是字面文本，不分段。候选前连续反斜杠数为奇数时才转义：移除最后一枚反斜杠，marker 保持正文；偶数时每对反斜杠输出一枚字面反斜杠，marker 仍可识别。因此 `\[[SEND]]` 保持字面 marker，`\\[[SEND]]` 保留一枚反斜杠并分段，`\\\[[SEND]]` 保留一枚反斜杠和字面 marker。唯一例外是整行仅由一对**配对** Markdown backtick 包裹的控制符，它按第 2/3 条识别，兼容模型把 marker 错误包成 code 的常见输出。
5. **与旧 Segmenter 的无歧义交接、优先级与审计。**每个 Batch 生成一个不出现在原文中的 UUID-based internal token，例如 `\x1ecompanion-send:<uuid>\x1f`；若碰撞则重新生成，直到 `segmenter_input` 不含该 token。Lexer 仅将识别 marker 替换为该 token，且 `SegmentOptions.Delimiter` 必须设为该 token，绝不能仍为 `[[SEND]]`。因此受保护/转义的旧 marker 不会被旧 Segmenter 二次拆开；Segmenter 完成后 token 不会出现在出站段。先识别 protected region 与转义，再识别双括号、最后识别单括号独立行；命中后统一折叠相邻/首尾空段。每个 companion Turn 的结构化 trace 写 `delimiter_rule_counts={double_inline,single_line}`、候选数与命中数，不记录额外原文。无法归类的近似写法保留为正文，不猜测“发送/分段”等自然语言。

### 6.4 Work-mode Projection、节流与 CardKit 操作

#### 有序投递与 drain barrier

每个 `turn/start` attempt 在 response 发出前创建 `TerminalArbiter` 与带 generation 的 attempt-local state；response 绑定后创建有序 `DisplayEvent` 管道。事件只可为：

```text
Bound(thread_id, turn_id)
Item(item_id, phase, sanitized_text)
Terminal(status_or_reason)
```

`turn/start` response 前到达的 display candidate 进入同一 attempt 的 pre-bind buffer：最多 64 条且序列化后的候选总量最多 256 KiB。response 绑定时 pump 必须先投递 `Bound`，再按 reader sequence 释放 buffer。early Terminal 不占 candidate cap，而是进入该 attempt 容量为 1 的 `PreBindTerminal` control；在 `Bound` 及所有已接受的 buffered Item 之后释放，重复 early Terminal 被拒绝。只有任一 candidate cap 超限或 candidate 无法绑定时，才通过 `TerminalArbiter` 以 `presentation_backpressure` 失败：停止接受展示 Item、只投递一次容量为 1 的 Terminal control、请求 interrupt；S03 raw/event/outcome 本地观察仍照常记录，但超限 Item 不进入 output state。

Runtime reader 对 post-bind `Item` 只做非阻塞 `TryPublish`，绝不等待飞书调用。attempt 内的单一 pump 将 Item 交给该 mode 的 Worker-owned output state（work 为 Projection，companion 为 final accumulator）；普通 Item inbox 同时上限为 64 条和 256 KiB 已序列化 `DisplayEvent` 字节。`TryPublish` 必须在 sanitizer 后、构造/复制 `DisplayEvent` 前原子 reservation count+bytes；单一 Item 超过剩余 byte budget 也立即失败，pump 消费后按该 Item 实际 reservation 释放。第 65 条或任一 byte reservation 失败时采用与 pre-bind 相同的 `presentation_backpressure` 终态，而不是无界 append、阻塞 reader 或假称已展示。`Bound` 在任何 pending notification 释放前先投递，因而 output state 从不接收未绑定 Item。

`TerminalArbiter` 是 attempt 唯一终态裁决者，原子状态为 `Active → Stopping(reason) → Terminal(cause,status) → Draining → Drained`；companion attempt 在创建 Arbiter 时一并创建 capacity-1 的 `DeliverySlot{cancel_requested,published,done}`。success Terminal 的 drain 后路径是 `DeliveryStarting → Delivering`，只有 slot `done` 后才 Drained。`DeliverySlot` 的 state、`BeginDelivery` 与控制命令使用同一 Worker mutex；`done` 在“未发布即被取消”和 Handle 收尾两种路径都恰好关闭一次。优先级如下：

1. `/new`、`/cancel`、`/stop` 和 Worker shutdown 在 Active 时先 CAS 为 `Stopping(control_reason)` 并取消 active turn；在已经成功 Terminal 的 Draining、DeliveryStarting 或 Delivering 时，它们仍必须在同一 mutex 下置 `DeliverySlot.cancel_requested`。若 Handle 已发布则取消其 context；若未发布则阻止 `BeginDelivery`。命令总是等待 slot `done` 后才能 archive、释放 Worker 或开始下一 Batch。
2. total/idle timeout、runtime exit、pre-bind/post-bind backpressure 仅在仍 Active 时 CAS 为 Stopping；它们随后 interrupt/失败收尾。
3. `turn/completed.status=completed` 仅在仍 Active 时可 CAS 为成功 Terminal；任何已 Stopping 的 completed 只能作为诊断 outcome，绝不恢复为成功或启动 delivery。
4. failed/interrupted terminal 同样只能从 Active 裁决；所有 late/duplicate event 在 Terminal 后拒绝。

work Projection 与 companion final accumulator 均严格按 App Server 到达顺序消费已接受 Item。Terminal 是 drain barrier：work 先消费所有已接受 Item、执行最后 flush 和关闭；companion 只在成功 Terminal 后按 latest non-empty final 调用上文的线性化 `BeginDelivery`，并仅在其发布 Handle 后发送，随后 ack Runtime；`StartTurn`/Worker 只在 Drained 后进入 Batch 成功/失败收尾和下一 Batch。此 ack 等待发生在 attempt/worker 控制协程，而不在 reader 中。

#### Projection 与操作账本

每个 active work-mode Batch 创建一个只被其 worker goroutine使用的 `CardProjection`：

```text
batch_id, app_id, channel_key, chat_group_id, thread_id, turn_id
message_id, card_id, mode(cardkit|patch), opening_state, open_uuid
seen_item_ids, progress_entries, final_text, final_item_id
stream_open, terminal, pending_flush_timer, pending_operation
```

1. Worker 在 `turn/start` 前打开初始 CardKit entity，并只发送一次引用同一 `card_id` 的 interactive message。实体发送不确定时不创建第二张可见消息；明确创建/发送失败才使用一次同 message PATCH/text 失败路径。
2. work 主路径的每次进展、正文与关闭均通过同一 `card_id` 的全量 `Card.Update(card_json)` 完成。每次全量更新使用严格递增 sequence；单次 update 明确失败时仅该次改走同一 `message_id` PATCH，下一次更新仍重试 CardKit。
3. Runtime 在 response 绑定的 attempt 中解析合格 `item/completed`，只投递归属 Worker 的展示值 `{item_id, phase, sanitized_text}`；不传递 raw JSON。
4. Projection 收到进展后立即更新内存，但最多每 250ms申请一次普通 flush；合并期间不丢 Item。final 与 terminal 进入高优先级队列，在适配器统一限速允许的最早时刻执行。
5. 全量 update 的网络/协议错误记录 operation、sequence 与稳定错误码；实现不把一次错误升级为 App 级永久熔断。终态 update 将 `streaming_mode=false` 写入同一份 card JSON。
6. 单次 CardKit update 的明确失败才对同一 `message_id` 做完整双区 PATCH；最终正文不能成功写入时，以受限速和字节预算保护的一次 text fallback 发送实际可见内容，Message 生命周期记录实际 message ID。

所有 adapter 调用在 JSON 序列化**之后**检查字节数：CardKit entity/inline PATCH 不得超过 28 KiB 安全预算；Text fallback 每段不超过 140 KiB UTF-8（飞书文本上限 150KB），按 rune 边界编号分段。单 Projection 有统一滑动窗口 limiter：CardKit 最多 10 ops/s，PATCH 最多 5 ops/s；final/terminal 为高优先级但不绕过限速。CardKit 流式模式 10 分钟后会自动关闭；S03 的 500 秒 turn 总时限仍早于此边界，终态仍主动关闭，不依赖自动关闭。

### 6.5 包边界与最小接口

| 边界 | 新职责 | 不拥有的职责 |
|---|---|---|
| `codexapp` | 将已绑定 attempt 的 allowlisted completed Item 解析、sanitizer 后以有界 DisplayEvent 管道按 Thread+Turn 投递，并等待 Terminal drain ack | 不构造卡片、不调飞书、不保存 UI 状态 |
| `worker` | work 的 `CardProjection`，companion 的 final accumulator、`TerminalArbiter`、`DeliverySlot`/`DeliveryHandle` 与分段发送调度，操作账本、去重、限速、Terminal drain 和跨 channel 隔离 | 不解析 raw JSON-RPC、不直接管理 App Server stdio |
| `output`/`feishu` | CardKit adapter、inline PATCH adapter、work 文字 fallback、companion plain-text segment sender 与 typed send outcome；对外超时和错误包装 | 不决定哪个 event 可展示、不重试 unknown send |
| `storage` | `MarkCompanionDeliveryStarted` 在首条可能可见发送前原子写入 batch ID/stage；`CompleteBatch` 或 `FailCompanionDelivery` 以 transaction 对全部同 batch、同 stage 的 processing Message 条件收尾并清除 stage；启动 reconciliation 只处理未能由当前 generation 收尾的 marker 行 | S04 不新增 segment-ID 表或 CardKit projection 持久化；非首段 ID/结果由本地 workflow trace 的 `batch_id/source_trace_ids` 保存，bot 整体重启不恢复 active delivery |

### 6.6 Work-mode 卡片状态与失败边界

```text
Opening → Streaming → FinalSeen → Closing → Closed
              │             │         │
              └── failure ──┴─────────┴→ Failed
```

- 同一 Turn 的晚到/重复 event、不同 Turn event、Closed/Failed 后 event 都不得更新卡片。
- CardKit entity 发送的明确失败允许进入 PATCH mode；SendUnconfirmed 禁止第二次可见发送并在启动 Turn 前确定性失败。两种明确初始发送均失败时才发送一次确定性文本并使 Batch 失败。
- 流式期间没有新增卡片按钮；日后引入回调时必须先关闭 streaming_mode。
- 每个飞书调用使用 10 秒 request timeout；它不会取消 App Server Turn。

### 6.7 Companion delivery 状态与重启边界

```text
ActiveTurn → SuccessTerminal → DeliveryStarting → Delivering(index=0…N) → FinalizingDB → Drained
      │             │                    │                    │                     │
      └── stop/fail ┴── cancel/exit ─────┴── cancel/exit ────┴── DB failure ────────┴→ Failed
```

- `DeliveryStarting` 是持久化 `companion_delivery_batch_id`/`delivery_stage` 后、Handle 发布前的显式状态；它和 `Delivering` 都仍属于原 Batch 的 InProcess。同 channel 的下一 Batch、`/new` 的 Thread 清理和 idle recycle 都必须等到 DeliverySlot.done。
- `/cancel`/`/stop` 在 `SuccessTerminal`、`DeliveryStarting` 或 `Delivering` 都置 cancel latch；未发布 Handle 时不得发送任何段，已发布时只取消未开始段。`/new` 也先取消并等 done，再 archive/clear Thread。任何 marker 已写入后的非成功路径，在关闭 slot 前必须等待 `FailCompanionDelivery` 成功或记录其最终 DB failure；已经从 Feishu 得到 response 的段绝不撤回或重发。
- delivery 中进程退出按用户 A 裁定结束；新 generation 不创建 DeliveryHandle、不补发余段，只对持久化 `delivery_stage=companion_delivery_started` 的 Batch 做条件 abandoned reconciliation。
- finalize transaction transient failure 只重试 transaction；若最终失败，不允许回到 Delivering。workflow trace 或 DB writer 失败都使后续未发段停止并形成稳定 error code，不能以静默成功释放 Worker。

| S04-AT-15 | Given marker 出现在 backtick/tilde fenced code、非整行 inline code、普通正文中的 `[SEND]` 或自然语言“发送/分段”、不配对 code wrapper、以及候选前 1/2/3 个反斜杠，When lexer **及随后 Segmenter** 扫描，Then 保护内容仍不拆段；1/2/3 个反斜杠分别输出字面 marker/一枚反斜杠后分段/一枚反斜杠和字面 marker。marker-only 的任何兼容形态仍走 `companion_final_empty` 安全文案。 |
| S04-AT-16 | Given 同库同时遗留 work processing、未进入 delivery 的 companion processing，以及两个因 generation 退出而未收尾、已标记 `companion_delivery_started` 的 companion Batch（其中一个已发送第 k 段），When 新 generation 启动，Then 不调用 SendText 重放或继续任何旧段；仅每个持久化 batch ID 所关联的全部 marker Message 条件变为 `failed/companion_delivery_abandoned`，清除 stage，abandoned trace 复用原 batch ID/完整 source traces 且不含正文；其它 processing 不被误标。 |
| S04-AT-17 | Given successful Terminal 前后 `/cancel`、`/new` 或 shutdown 与 companion delivery 交错，When `TerminalArbiter`/`DeliverySlot` 线性化，Then cancel 先获胜时 `SendText=0`；已发布时只取消尚未完成的 delay/API/retry；所有控制路径都等 slot done 后才释放 Worker。该机制以 focused unit tests 验证。 |
| S04-AT-18 | Given response 前的 early Terminal、response 前第 65 条 candidate、256KiB candidate bytes，或 bound 后第 65 条、单条 256KiB+1、64 条合计超 256KiB 的 Item 以及 pump 并发释放 reservation，When reader `TryPublish`，Then early Terminal 以容量为 1 的 control 在 Bound 与已接受 Item 后释放；其余超限场景 reader 不阻塞、S03 本地事件仍有证据、无超限大文本进入 output state、arbiter 仅一次以 `presentation_backpressure` interrupt/安全收尾；没有无界 append、spill queue、reservation 泄漏或第二个 Terminal。 |
| S04-AT-19 | Given final A、重复 A、final B、late commentary/final 与 Terminal 交错，When 同 Turn 到达，Then 同 item.id 只计一次，Terminal 前 latest non-empty B wins，Terminal 后 Item 被拒绝，companion 只发经其 lexer 清洗后的 B 一次；work 与 companion 选择同一 latest final Item，文本清洗差异由 AT-14/15 单独断言。 |
| S04-AT-20 | Given 一个 Batch 含 2–3 条 processing Message，When `MarkCompanionDeliveryStarted`、sent/rejected/unknown/cancelled ledger 完成、trace writer/local delivery failure、任一 UPDATE rows=0、commit transient/permanent failure 或重复 finalize，Then stage 标记全部写入或 rollback；`CompleteBatch` 与 `FailCompanionDelivery` 均为全部同 batch/stage 条件更新或全部 rollback/清除 stage；DB retry 不增加 SendText；只有本 generation 最终未能 fail-finalize 的 marker 行才在重启时 abandoned，绝不重发可见段。 |
| S04-AT-21 | Given SendText 首次 429、第二次 429、明确 rejected、服务端可能接受但客户端 timeout/connection close，When 交付，Then 429 仅重试一次且两次 trace 分别为 `rejected/rate_limited/retry_count=0` 与 `retry_count=1`；rejected 按旧语义继续后续段；unknown 不重试当前段且停止余段，summary/trace 准确记录 `rejected`/`unknown`，不把 unknown 当 sent。 |
| S04-AT-22 | Given 每段 API result 或 workflow trace writer failure，When delivery，Then可失败 workflow JSONL writer 在下一段前写入规定 schema、SHA-256 digest 与 batch/source trace 关联且无正文；writer failure 停止余段并以 `companion_delivery_trace_incomplete` 收尾。 |
| S04-AT-23 | Given 多 Message Batch 的不同 trace_id，When companion 发送 N 段并完成/partial/abandoned，Then 每个 delivery event 都含同一持久化 batch_id、完整 source_trace_ids、turn_id 和 segment_index；所有 Batch Message 的 transaction outcome 一致，查询不会把某一 source trace 误当唯一 owner。 |
| S04-AT-24 | Given `companion_segment_delay_ms` 默认 400、固定 RNG/fake clock、不同 rune 数以及缺失/0/2001 的配置，When 启动并发送三段，Then 启动默认/校验进入 `streaming` config schema，且该字段只覆盖旧 SegmentOptions 的 BaseDelay；首段 300–1500ms、后续 600–2000ms、429 backoff 500ms 与 cancel 唤醒均可确定性断言，不使用真实 sleep。 |

L1 覆盖 mapper、Projection、大小预算和 Card JSON renderer；L2 使用 fake CardKit、fake PATCH、fake App Server 与 fake clock；L3 用真实 App/SDK 创建与关闭一张 CardKit entity；L4 用真实飞书确认同一 message ID 的进展更新和最终正文。

## 10. 风险、残留项与后续 Story

| 风险/残留 | 当前控制 | 后续责任 |
|---|---|---|
| App 未获 CardKit 权限或客户端过旧 | 实现前 preflight；PATCH 保持可读降级，但不当作 CardKit 验收 | App 配置/运行手册。 |
| 长进展或最终答复超过 CardKit 30KB | 明确 byte 预算和 text fallback，不静默截断 | 长内容/文档交付 Story。 |
| bot 整体重启时仍有流式卡 | 沿用 S03 不恢复活跃 Turn；飞书 10 分钟自动关闭，后续可增加持久化卡片恢复 | Runtime recovery Story。 |
| `final_answer` 缺失或未来 phase 漂移 | 明确“无 final 不冒充答案”；未知 phase 忽略并记录稳定诊断字段 | App Server 升级验证。 |
| 卡片按钮与流式回调互斥 | 本期不放按钮，终态关闭流式 | Command/Approval Story。 |
| 展示策略过度暴露 | allowlist 限定 agentMessage text；禁止 raw、reasoning、工具、用户输入 | 后续展示策略评审。 |
| companion 分段体验与旧 bot 漂移 | 明确复用旧 `SplitSegments`、延迟与逐段错误语义，并用原有 fixtures/新 L4 对照 | Companion UX 回归测试。 |
| 模型生成了近似但非标准 marker | 先以候选归一化+受限 RE2 兼容，再以 code/转义保护避免误拆；不把自然语言猜成 marker | Lexer fixture 扩充与 LI-02。 |
| companion delivery 中进程退出 | 用户选择不恢复、不重发；启动时仅标记可能部分可见的 abandoned 状态 | Runtime recovery Story 不引入 segment ledger。 |
| 旧 persona 过滤质量 | 本期不迁移 Claude hook；需要时后续建立 Codex-native output-policy Story | 产品/输出策略 Story。 |
