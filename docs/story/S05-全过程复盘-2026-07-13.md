# S05 全过程复盘：附件输入与飞书能力代理

> 完成日期：2026-07-13
> 交付结论：Delivered（按用户明确允许纳入本次实现期历史真实成功记录的验收边界）

## 1. 实际交付

S05 建立了从飞书 image/file 事件到 Codex Turn 的完整附件链路：先进行 receipt 去重和 staging，再由同一 channel Worker 按 FIFO 下载、限流式写入、原子落盘，并把真实可读本机路径传给 App Server；图片另以 `localImage` 传入，普通文件使用文本 manifest。

同一 Turn 可调用受绑定上下文约束的 `feishu` dynamic tools：向当前会话发消息、上传并发送任意本机普通文件、创建并公告 Markdown 飞书文档、读取当前 App 有权访问的 docx 文档。模型不能指定接收人、App 或凭据。个人本机策略不设目录白名单；仍拒绝非 regular file、空文件、超限文件和跨会话发送。

文件发送按内容签名分流：符合飞书 image API 且不超过 10 MB 的图片以原生图片消息发送，其他内容走文件消息。文档创建使用 `create docx -> Markdown Convert -> descendant blocks`，避免只创建空文档或把 Markdown 原样当纯文本。

## 3. 发现的问题与永久改进

| 问题 | 根因分类 | 修复与预防 |
|---|---|---|
| 文件上传被限制在 attachment/workspace 目录 | 过期的产品边界假设 | 用户明确这是个人本机工具后，移除目录白名单；保留 regular-file、大小与当前 channel 约束。 |
| App Server 不知道附件位置 | 协议输入契约不完整 | manifest 显式携带实际可读本机路径，图片另传 `localImage`；不使用不存在的 file input schema。 |
| 进展区在无 delta 的 Final Answer 后不刷新 | 终态投影遗漏 | Final Answer 到达而本轮没有进展更新时，清空进展区，避免用户看到陈旧进度。 |
| Markdown 文档为空或未渲染 | 飞书 docx 写入 API 使用不完整 | 采用 Markdown Convert 后批量写 descendant blocks，并处理只读 merge metadata。 |
| 飞书文档无法读取 | Story 能力缺口 | 增加 `feishu.doc_read`，只读当前 App 有权访问的 docx URL/ID，正文只回 tool result。 |
| 图片以文件方式发送 | 外部 API 分支遗漏 | 由生产发送路径按文件签名选择 image/file API，并为原生图片补真实 L4 冒烟。 |
| 重启后旧 action 缓存无法解密 | 稳定 key 只存在于短生命周期环境 | 文档化稳定 key 配置与 keyring 校验；旧密文恢复影响作为残留风险记录。 |
| 验收记录仍称外部 action 未测 | 交付证据没有随用户验证回写 | 用户确认历史真实成功可计入验收后，重写集成记录、DoD 和 Story 状态，消除相互矛盾。 |

## 4. 用户裁定的残余边界

- 不引入本地共享限流、自动退避或目录权限模型；用户明确负责个人本机使用节奏与文件范围。
- 不支持 audio、media、post 内嵌资源、任意 URL 下载、云盘搜索、跨会话发送、文档编辑/owner transfer；这些需要独立 Story。
- 超过飞书原生 image API 10 MB 上限的图片按文件消息发送，保持可交付但不承诺图片预览。
- 非 S05 调用链的 p2p chat-enter event 仍可能产生无 handler 告警；后续 ingress hygiene 工作处理。
