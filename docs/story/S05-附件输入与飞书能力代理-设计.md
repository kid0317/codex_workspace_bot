# S05：附件输入与飞书能力代理

> **状态**：Delivered（2026-07-13；本机门禁、App Server L3、真实飞书 L4 与最终 blocker-only 复审均已闭环）

## 1. 一句话目标

让本机 Codex Feishu Bot 的用户可以把**图片或文件**发送到当前 p2p/group 会话，并让 Bot 在同一 channel 的 FIFO 中安全下载、暂存并交给 Codex；同时让 Codex 通过一个不暴露凭据、不允许越会话寻址的飞书能力代理，完成当前会话的发消息、上传并发送文件、创建飞书文档。

## 2. 背景

当前入口 `internal/feishu.Normalize` 只接受 `message_type=text`，`messages` 只保存正文，`codexapp.Processor` 只向 `turn/start` 传入一个 text input。因此收到 image/file 不是“少一个下载 API”，而是缺少从 receipt、同 channel 调度、持久化状态、受控本地文件到 App Server 输入的完整链路。

本 Story 对照了两套旧实现：

- XiaoPaw S11 的正确边界是先把资源引用与消息放入同一 channel 的 FIFO，再由 Worker 下载并构造 Turn；这避免附件下载抢占后续文本的顺序。它的 `file/image`、下载 type 映射、required/optional 下载语义与脱敏观察值得复用。
- XiaoPaw S12 的正确边界是 Agent 只调用 allowlist action，服务端从可信会话上下文推导 App、用户和 channel；不能把 app secret、chat ID 或任意目标发送能力交给模型。
- 旧 CC Workspace Bot 的用户价值（图片/文件输入、`send_text`、`send_file`、`create_doc`）可复用，但其 callback 内下载、`/tmp -> Rename`、绝对路径写入 prompt、SQLite 索引、workspace 内凭据和模型传入 `routing_key` 均违反本项目的 MySQL、同频道串行和凭据隔离契约。

本机在 2026-07-12 用 `codex app-server generate-json-schema --experimental` 生成的 v2 schema 已确认：`thread/start.dynamicTools` 可声明 function/namespace 工具；App Server 以 `item/tool/call` server request 交付 `threadId`、`turnId`、`callId`、`tool` 和 `arguments`，客户端回 `{success,contentItems}`。同一 schema 支持 `localImage{path}`，但**没有通用本地 file input**；S05 对普通文件使用受控文本 manifest，图片额外使用 `localImage`，不假设过期文档中的 `{type:"file",path:...}` 仍可用。

## 3. 范围

### 3.1 本期做什么

1. 接收有效 p2p/group 的 `image` 与 `file` 飞书消息；附件-only 消息也是可处理输入，不要求用户再补一条文本。
2. 在下载前完成既有 receipt/idempotency、`messages`/附件 staging 持久化和当前 `group:{chat_id}:{app_id}` 或 `p2p:{sender_open_id}:{app_id}` Worker 入队；WS callback 不下载、不读写临时文件。合法 event 的附件内容解析失败也必须持久化为确定性 failed receipt，不能靠“不落库”反复重投。
3. 由 owning channel Worker 按 FIFO 下载附件，以流式上限、临时文件和同目录原子 rename 保存至 session-scoped 本地根目录；下载成功才启动该 Batch 的 Codex Turn。
4. 为每个附件持久化最小可恢复 metadata、下载状态和清理期限；图片以 schema 已验证的 `localImage` 传入，普通文件通过无 resource key 的文本 manifest 传入，均不把真实宿主绝对路径写入 MySQL 正文、普通日志或 Langfuse。
5. 在 `thread/start` 注册 `feishu` dynamic-tool namespace，并精确处理已绑定 Turn 的 `item/tool/call`：`feishu.message_send_current_channel`、`feishu.file_upload_and_send_current_channel`、`feishu.doc_create_and_announce`、`feishu.doc_read`。动态工具的 `name` 只使用字母、数字、下划线和连字符，逻辑分组由 namespace 承担。
6. 在 bot 进程内提供 action proxy：从已绑定 `app_id/channel_key/chat_group_id/thread_id/turn_id` 推导凭据和当前 reply target；模型不能覆盖 app、chat、open_id、credential 或 route。`feishu.file_upload_and_send_current_channel` 例外地接受任意本机普通文件的 `file_path`，以满足个人本机使用场景。
7. 增加 MySQL forward-only migration、附件 retention 清理、配置模板、测试 App 权限预检、fake/L3/L4 验收及脱敏 action/attachment 观察记录。

### 3.2 本期不做什么

- 不支持 `audio`、`media`、富文本 `post` 内嵌资源、历史消息回补、多附件富文本顺序重建或 OCR/转码；这些是 S05 后续扩展，不得被 image/file parser 静默当作 text。
- 不支持模型指定任意 chat、任意 user、`routing_key`、`receive_id`、app ID 或 app secret；但 `feishu.file_upload_and_send_current_channel` 可上传任意本机普通文件路径。
- 不实现任意网络 URL 下载、云盘浏览/搜索、文件分享/权限管理、跨 App 复制、文档编辑/追加/批量创建或文档所有者转移。
- 不把附件原文、resource key、文件内容、完整原始文件名或真实绝对路径写入 Langfuse、常规日志、`messages.user_content` 或 dynamic-tool 返回文本。
- 不新增 Redis、SQLite、workspace `feishu.json`、每个 workspace bridge file、CLI credential profile 或每 App App Server child。
- 不在本期把外部副作用接入审批卡；已选择的个人本地策略是：在当前绑定 Turn 内、由用户任务明确触发的当前会话动作可自动执行。若要“每次发出前确认”或跨会话发送，另开 Approval/授权 Story。

## 5. 核心设计决策

| 问题 | 结论 | 原因 | 后果 |
|---|---|---|---|
| 下载发生在哪里 | receipt + staging + 入队后，由同 channel Worker 下载 | 维持同 channel FIFO，避免 WS callback 被大文件/网络卡住；重复 event 不重复下载。 | 下载是 Worker attempt 的可取消步骤；下载失败只收尾该附件 Message，后续消息继续。合法 event 的附件 JSON/resource ref 无效时，事务写 `messages.status=failed,error_code=attachment_invalid` 作为 receipt，不建 attachment row、不入队。 |
| Batch 边界 | 含 required attachment 的 Message 是不可合并边界：它自己形成一个 Batch；其后的 FIFO Message 必须留到下一 Batch | 当前 Worker 会把 queue drain 的所有消息合并；若不切边界，附件失败会误伤后续文本且不能证明顺序。 | `[text,text,attachment,text]` 可形成 `[text,text] -> [attachment] -> [text]`；attachment 下载失败只失败中间 Batch，下一 Batch 正常继续。 |
| 入站支持面 | P0 仅 `image`、`file`，每条消息至多一个下载资源 | 对齐用户目标，避免把 S11 的 audio/media/post 一次性带入。 | 其他 message type 忽略或按现有 text 行为处理，绝不误报“附件已处理”。 |
| 本地文件策略 | `attachments.root_dir` 默认为 `.codex-workspace-bot/attachments`，也可设为任意相对或绝对本机路径；实际 payload 仍按 app/channel/session/attachment 分层，方便 retention 清理，但不施加目录访问白名单或显式 chmod。 | 产品仅供用户个人本机使用，用户明确要求 Agent 可操作任意本机路径。 | session-id 只服务于附件状态与清理，不构成读写边界；App Server manifest 直接提供可读本机路径。 |
| 文件大小/MIME | 配置默认单附件 30,000,000 bytes（30 MB）、单 Batch 30,000,000 bytes（30 MB）；以 `max+1` 流式读取拒绝超限；声明 MIME 仅作提示并记录 observed MIME | 取飞书 file upload 的较小安全上限，阻止截断文件被当成功，同时不因常见 `application/octet-stream` 拒绝普通文件。 | image 必须通过受支持 image decoder；file 接受任何非空 regular bytes（不自动执行），unknown MIME 可用；Bot 只承诺安全保存并提供给 Codex 读取，不承诺每种格式都能理解。仅超限、空/危险文件对象或 image 无法解码为 `attachment_invalid`/`attachment_too_large`，清理 `.part`。 |
| App Server 输入 | 图片：先传含实际本机路径的非空文本 manifest，再传 `localImage{path,detail:"auto"}`；普通文件：文本 manifest 含实际可读本机路径、kind 和 safe display name，Agent 自行按路径读取。 | 当前真实 v2 schema 没有 generic file input；用户要求明确把路径交给 App Server。 | 不写 `{type:"file"}`；附件-only 消息不得添加空 `{type:"text"}` 占位，因为 text input 的 `text` 是必填；路径仅进入该 Turn protocol，不写常规日志或消息正文。 |
| 动态工具 | `thread/start.dynamicTools` 注册单一 `feishu` namespace，App Server `item/tool/call` 经 attempt-owned executor 执行并由唯一 client writer 回 protocol-correct result | 这是本机 schema 已提供的 Codex-native client tool 机制，不需向 workspace 写凭据或 bridge files；网络动作不能阻塞 JSON-RPC reader。 | S05 **只在 L3 证明新 Thread 经 `thread/resume` 仍保留 catalog 时进入 Ready**。新增 `doc_read` 后，旧 catalog 必须在空闲边界 archive + CAS clear，当前 Batch 懒创建带 `toolset_version=s05-feishu-v2` 的新 Thread；若新 Thread 不保留，S05 保持 Draft，另开协议兼容设计，绝不以每轮新 Thread 或 prompt shell 命令降级。 |
| 副作用边界 | 写操作仅当前绑定 App + channel；p2p target 是该消息 sender `open_id`，group target 是事件 `chat_id`；读文档只使用当前 App 的飞书授权，不从模型接收 token/credential | 与 routing/tenant isolation 契约一致，拒绝 prompt injection 把结果发到外部。 | 模型参数只描述 text、`file_path`、markdown ref、title、document URL；server 推导 target/credential/folder。 |
| 文件可发送范围 | `feishu.file_upload_and_send_current_channel` 可上传任意本机普通文件，不限 attachment session、workspace 或目录；受飞书 image API 支持且不超过 10 MB 的图片以原生图片消息发送，其余内容以文件消息发送。 | 用户已明确这是个人本机工具，常需发送其他目录的文件；图片作为文件卡片会丢失预览体验。 | 工具描述要求模型传绝对 `file_path`；兼容接收相对路径。以文件内容签名识别 JPEG、PNG、GIF、WEBP、TIFF、BMP、ICO，避免仅信任扩展名；解析 symlink 后目标必须是可读 regular file（拒绝目录、socket、device、FIFO），以同一已打开 fd 流式上传，仍执行文件 30 MB/非空约束。 |
| doc 创建语义 | `feishu.doc_create_and_announce(markdown_ref,title?)` 读取任意本机 UTF-8 regular Markdown，按 `create docx -> Convert(Markdown) -> DocumentBlockDescendant.Create` 创建文档；飞书负责保留 Markdown 的标题、列表、代码块、引用、待办和表格语义，单次至多插入 1000 个转换后的 Block；表格的只读 `merge_info` 在插入前移除；无论内容完整与否都尝试向当前 channel 发 doc URL，返回 `{document_id,url,content_written,announcement_outcome}` | 创建 URL 是用户价值，不能依赖模型后来是否把 tool result 写进 final。 | 工具描述要求模型传绝对 `markdown_ref`；实现兼容相对路径。title 1–800 plain-text chars，Markdown 大小与批量 blocks 上限须预检；后续 block 转换/插入失败返回已创建 URL + `content_written:false`，不伪称完整成功。owner transfer 不在本期。 |
| doc 读取语义 | `feishu.doc_read(document_url)` 从有效飞书 docx URL 提取 document ID，并以当前 App 的 `Docx.Document.RawContent` 读取正文；只将正文作为当前 Turn 的 tool result 返回给 Codex | 用户在当前会话提供文档 URL 后，应能直接进入阅读/学习流程，无需下载、粘贴正文或让模型自行绕过鉴权访问 URL。 | 仅接受 docx URL 或 document ID；服务端不接收 token、cookie 或任意网页 URL。正文不写普通日志、消息正文或 Langfuse；encrypted action ledger 可保存同 call 的结果以支持 protocol replay。飞书拒绝访问时返回明确的安全失败结果，不伪称“已读”。 |
| 重试与幂等 | 下载可按稳定错误类别有限重试；外部写入以 `(app_id,thread_id,turn_id,call_id)` 原子 claim 并持久化 ledger；HTTP/network unknown 不盲目重发 | 外部动作可能已可见，不能因本地超时制造重复文件/文档/消息。 | 状态机为 `claimed -> in_flight -> succeeded|rejected|unknown|cancelled_before_send`；同键同 arguments digest 等待已在途调用至 action deadline 或返回 `in_progress`，同 callId 异 digest 拒绝；进网后 cancel/exit 只能 `unknown`。 |
| 限流处理 | S05 不实现本地共享限流器、排队器或 429 自动退避 | 用户已明确是个人本机使用，并接受自行避免触发外部限流。 | 飞书明确返回 429 时 action 记为 `rejected` 并把安全失败结果回当前 Turn；不自动重试，也不以新 callId 重试。 |
| 清理与重启 | 成功/失败附件按 `attachments_retention_days`（默认 7）清理，绝对上限 `attachments_max_days`（默认 30）；attachment session 持有 `attempt_id/lease_until` | HLD 已给出 retention 意图，S05 将其变为可执行且可查询的契约。 | 删除前 DB CAS 标记；lease 未过期绝不删除。bot restart 将 queued/processing attachment 安全置 failed、清理 `.part`、不重放下载/Turn；过期 lease 才由 reconciler 清理。 |

## 6. 主链路与数据/接口契约

### 6.1 入站、暂存、下载和 Turn

```text
Feishu WS image/file
  -> NormalizeAttachment（仅解析安全 metadata/resource reference）
  -> PersistIncomingWithAttachments（receipt 去重 + message=received + attachment=staged）
  -> current channel Worker FIFO
  -> Mark message/attachment processing
  -> AttachmentProcessor: resource download -> limits/hash/MIME -> .part -> atomic rename
  -> build input: text manifest + localImage(s)
  -> thread/resume or thread/start(dynamicTools) -> turn/start
  -> normal existing card/text terminal delivery
```

1. `RawEvent`/`router.Incoming` 改为明确的 `Text` 与 `[]AttachmentReference`，不把 `[文件: ...]` 编码进 `Text`。
2. `PersistIncomingWithAttachments` 是一个事务：按现有 `(chat_group_id,feishu_event_id)` 去重；重复时不新建 attachment、也不入队。新消息写 `messages`，再写附件 rows；合法 event 的引用解析失败则写安全占位 `user_content`、`status=failed,error_code=attachment_invalid` 作为 receipt，不建 attachment、不入队，重投只命中该终态。
3. Batch builder 在遇到含 required attachment 的 Message 时停止当前 drain：该 Message 单独 Batch，其后 Message 留在 queue。Worker 取得附件 Batch 后先把 attachment 标 `processing` 并写 `attempt_id/lease_until`；下载失败只让该 Batch failed，后续同 channel Batch 继续；不能在未下载附件时启动 Turn。
4. 下载使用与该 App 对应的 Feishu client，请求为消息 ID + resource key + 对应 resource type；key 只在内存和受保护 DB 字段使用。文件以 `O_CREATE|O_EXCL` 创建 `.part`，限制为 `limit+1`，写完 `fsync` 后 rename 到同目录 payload；失败删除 `.part` 与空目录。
5. Turn 只收到 `AttachmentManifest`：`attachment_id`、kind、safe display name、observed MIME、byte size 和实际可读本机路径。图片再附 `localImage`；普通 file 不伪造 schema 不存在的 `file`。路径不作为访问控制边界，仍不得写入常规日志或消息正文。

### 6.2 新存储与配置

新增 `attachments` 表，不向 `messages.user_content` 塞 JSON；`chat_groups` 增加 nullable `codex_toolset_version`。只有写入 `s05-feishu-v2` 的 Thread 可被当作带 `feishu` dynamic tools 的 session；旧值/空值必须在 owning Worker 的空闲边界 archive + 条件清空 thread ID，再由当前 Batch 懒创建新 Thread。该升级会中断旧 Thread 的连续上下文，必须在同一张处理卡/安全文本明确告知“会话已升级，已开始新的 Codex 会话”。

| 字段 | 约束与用途 |
|---|---|
| `id` | UUID，主键，也是 tool `file_ref` 的不透明引用。 |
| `message_id`, `chat_group_id` | 外键；保证归属可从 DB 校验。 |
| `kind` | enum `image|file`。 |
| `source_resource_ref_enc`, `source_ref_key_version` | 使用 active key 的 AES-256-GCM 加密的飞书 resource key，AAD=`app_id|attachment_id|source_message_id`；日志仅记录 SHA-256 digest，**不得使用 base64 伪装为加密**。成功下载或最终失败后清空密文。 |
| `source_message_id`, `original_name_safe` | 受限字段；display name 经过控制字符、路径分隔符和长度清洗。 |
| `declared_mime`, `observed_mime`, `byte_size`, `sha256` | 下载完成后写入；SHA-256 为小写 hex。 |
| `session_id`, `relative_path` | 只保存相对路径；唯一键 `(session_id,relative_path)`。 |
| `state`, `error_code`, `attempt_id`, `lease_until`, `retention_deadline`, `deleted_at` | 状态机 `staged -> processing -> ready|failed -> deleting -> deleted`，所有转移有条件更新；lease 使 cleanup/restart 能判断是否仍有 active owner。 |

新增 `feishu_action_calls` ledger：复合唯一键 `(app_id,thread_id,turn_id,call_id)`；字段包含 `channel_key/chat_group_id/tool/arguments_digest/state/result_enc/result_key_version/object_id_digest/error_code/created_at/completed_at`。`result_enc` 以独立 action-result AES-256-GCM key 加密，AAD 绑定该复合键和 tool；日志只用 `object_id_digest`。不保存正文、token、真实路径或 tool argument 原文。同键同 digest 的完成调用解密并返回同一结果；同 callId 异 digest 拒绝；unknown 永不自动重发。

两类 encryption key 都由版本化 keyring 配置提供：`{version,key_env}`，active key 加密、历史 key 只用于尚未清理数据解密；环境变量必须是 base64 编码的 32-byte key。启动时任何 enabled App 所需 key 缺失/长度错误即 fail-closed；轮换先加入新 active key，待旧 attachment/action retention 到期后移除旧 key。密文、nonce、key version 只存在受限 DB 字段，绝不进入日志。

新增配置：

```yaml
attachments:
  root_dir: ".codex-workspace-bot/attachments" # 可替换为任意相对或绝对本机路径
  max_file_bytes: 30000000
  max_batch_bytes: 30000000
  download_timeout_seconds: 30
  retention_days: 7
  max_retention_days: 30
  resource_ref_keys:                       # active key first；key_env 不进版本库
    - version: 1
      key_env: "CODEX_WORKSPACE_BOT_ATTACHMENT_KEY_V1"
feishu_actions:
  enabled: true
  default_doc_folder_token: ""          # 每 App 覆盖；空为 App 根目录
  action_timeout_seconds: 20
  result_keys:
    - version: 1
      key_env: "CODEX_WORKSPACE_BOT_ACTION_RESULT_KEY_V1"
```

现有 HLD 的 cleanup 名称在实现时统一迁移到上述 `attachments` schema；不得出现两套相互矛盾的 retention 来源。

### 6.3 Dynamic tools 与可信 action proxy

`thread/start` 追加以下概念性 tool catalog（实际 JSON 以 schema preflight 生成）：

| Tool | 模型允许参数 | 服务端推导/验证 | 成功结果 |
|---|---|---|---|
| `feishu.message_send_current_channel` | `text` | active app、当前 p2p/group reply target、最大文本大小、callId | `{message_id}` |
| `feishu.file_upload_and_send_current_channel` | `file_path`, `display_name?` | 任意本机 ordinary file、大小/MIME、当前 target | `{file_key_digest,message_id}` |
| `feishu.doc_create_and_announce` | `markdown_ref`, `title?` | 任意本机 UTF-8 regular Markdown、default doc folder、title、当前 channel announcement | `{document_id,url,content_written,announcement_outcome}` |
| `feishu.doc_read` | `document_url` | 从 docx URL/ID 提取 document ID，当前 App 的 `RawContent` 权限与访问范围 | 文档纯文本，仅作为当前 Turn 的 tool result |

**Client/Runtime 协议改造是本 Story 的显式范围。** 当前 client 的 read loop 对 server request 统一预拒绝、Runtime 又会结束 attempt；S05 必须替换为单一 `ServerRequestRouter`：reader 只分类、关联和投递；唯一 serialized stdout writer 只由 router 的 response path 写 JSON-RPC result。未知 server request 才回 `-32001`；`item/tool/call` 不可先写 error 后再由 Worker 写第二个 response。

`item/tool/call` 可能早于 `turn/start` response。attempt 已知 `thread_id`、未知 `turn_id` 时，reader 将同 thread 的工具 request 放进有界 pre-bind buffer（最多 16 个或 64 KiB，直到 RPC deadline）；`turn/start` response 绑定后只释放 exact turn 的 request。deadline、mismatch、重复 request ID、Worker 失去所有权或 cancel 都回一次安全 failure，绝不触发飞书副作用。该 buffer 与现有 presentation-event buffer 分离，且同样必须在 generation exit 时一次性完成拒绝。

处理已绑定 `item/tool/call` 的顺序必须是：

1. 先匹配当前 Runtime attempt 的 exact `threadId + turnId`，并确认 Worker 仍持有该 attempt；mismatch、late、unknown tool 或重复 active call 都回 `success:false` 的安全文本，不触发副作用。
2. 投递给 attempt-owned、bounded action executor（depth 4）；reader 不同步做 Feishu I/O。executor context 由 active turn 派生，cancel/stop/exit 取消尚未进网的 job；worker 从不直接写 App Server stdin。
3. 原子创建/读取 action claim 后校验可信 route；模型参数中存在 `app_id/chat_id/open_id/routing_key/credential/folder_token` 直接拒绝。`file_path` 仅为 file upload action 的合法业务参数。
4. proxy 取得该 App 的内存 Feishu client 和由 `ReplyTarget` 推导的 `receive_id_type/receive_id`；SDK/HTTP adapter 有明确 deadline、stable error mapping 和 request UUID；S05 不加本地 rate governor 或 retry queue。
5. 网络调用开始前条件更新为 `in_flight`；先持久化已知 terminal outcome，再由唯一 writer 向 App Server 回符合 schema 的 `contentItems:[{type:"inputText",text:<redacted JSON result>}]`。失败不得将 token、API 原文、完整外部 ID 或绝对路径带回模型。
6. `turn/interrupt`、`/cancel`、`/new`、Worker stop 或 App Server exit 取消尚未进网的 action 并标 `cancelled_before_send`；已进网 action 一律以 `unknown` 收尾，不重发。

`thread/resume` 的 dynamic-tool persistence 是必须验证的协议事实：L3 必须证明 S05 新 Thread resume 后仍有正确 catalog 并能执行一次 fake call；S05 前的 persisted Thread 因创建时无 catalog，按上节 toolset version 升级，不可假定 resume 能回填 `dynamicTools`。若 schema/实测表明 S05 新 Thread 也不保留，本 Story不进入 Ready，必须先用官方支持的 thread update 机制另行设计/评审；不能偷偷在 prompt 中塞 shell 命令替代，也不能用每轮新 Thread 换取工具可用。

### 6.4 错误、状态和可观测性

| 场景 | 用户可见结果 | DB/日志稳定事实 |
|---|---|---|
| resource 下载超时/403/不存在 | “附件无法下载，请重新发送或检查权限。” | `attachment_download_failed`，attachment failed，记录 kind/size bucket/trace。 |
| 超限、MIME/文件不安全 | “附件大小或类型不受支持。” | `attachment_too_large` 或 `attachment_invalid`，删除半文件。 |
| tool 伪造 route/路径或过期 Turn | 安全 tool failure，不发送飞书消息 | `feishu_action_rejected`，记录 tool/call digest/reason。 |
| 飞书明确 4xx | tool 返回可行动的安全失败 | `rejected`，不重试。 |
| 429 | action 返回当前 Turn 可见的“飞书请求被限流，请稍后自行重试”；不实现本地退避或自动重试 | `rejected`，ledger 保留。 |
| 5xx/timeout | 不自动重试；未知响应不重试 | `unknown`，ledger 保留。 |
| doc 已创建而后续 Markdown block 写入失败 | 返回 document URL，标 `content_written:false` | 记录 document ID digest 与 `doc_content_partial`，不误报“文档未创建”。 |
| doc 已创建但 URL 公告失败 | 当前 Turn 的安全结果明确“文档已创建但链接发送失败”，并保留 URL 供该 Turn 的正常终态交付 | `announcement_outcome=rejected|unknown`，不把文档创建改写为失败，也不使用新 callId 自动重发。 |

每个 attachment/action 事件必须带 `app_id`、`channel_key`、`chat_group_id`、`trace_id`、`thread_id`、`turn_id`（存在时）、`attachment_id/call_id`、`event/result/error`；其中外部 ID 与 resource key 只记录 salted hash/digest。禁止正文、文件内容、token、Authorization、完整 file name、绝对路径进入 `slog`、workflow JSONL、MySQL message 正文或 Langfuse。Langfuse 仍仅 fail-open metadata。
