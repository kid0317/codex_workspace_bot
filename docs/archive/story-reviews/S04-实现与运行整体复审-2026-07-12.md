- 自动测试、race、vet、build 及 Story SOP/DoD。

报告不记录用户正文、assistant 正文、凭证、token、原始 payload 或飞书 Chat/Open ID。

## 3. 设计—实现一致性矩阵

| S04 契约 | 当前实现 | 判断 |
|---|---|---|
| work：同卡双区、进展与正文分开、完成状态明确 | `RenderWorkCardJSON` 生成进展 panel、`hr`、正文，标题为“生成中/已完成”；worker 投影并在 final/terminal PATCH。 | **已实现，真实 PATCH 路径已验证。** |

| 250ms flush、5/s PATCH/10/s CardKit、28KiB/150KiB budget | 每个可见 item 直接调用 `UpdateBatchCardZones`；没有 timer、limiter、序列化大小检查或文字 fallback 分段。 | **未实现。** |
| pre-bind/post-bind 64 + 256KiB、TerminalArbiter 单裁决 | work 仅有 callback channel 的 64 条/256KiB reservation；runtime callback false 后异步 interrupt。无 pre-bind buffer、TerminalArbiter、稳定 `presentation_backpressure` 终态或对应状态机。 | **部分实现，关键竞态契约缺失。** |

## 4. 发现

### Blocker

| ID | 发现与证据 | 风险 / 必须整改 |
|---|---|---|
| B-01 | **CardKit 主路径完全未实现，且无 L3/L3b。**设计把 CardKit entity、stable UUID、element update、sequence 和 settings close 定为主体验（[S04](../../story/S04-双区流式卡片展示-设计.md#L190-L197)）；实现只走 `CreateMessage` 与全卡 `Message.Patch`（[feishu.go](../../../internal/feishu/feishu.go#L77-L122)）。 | PATCH 成功不能被当作 CardKit 验收。实现 adapter/ledger、SDK preflight 与真实 L3/L3b，或重新裁定并回写 S04/HLD，把 PATCH 升格为正式主路径。 |
| B-02 | **companion 核心交付语义尚未实现。**配置值只在 `config` 解析/校验，未传入 worker（全仓唯一业务引用仅 config）；分段函数仅 `strings.Split`，没有旧 fallback、80-rune、短段合并、独立行 `[SEND]`、打字延迟或 fake clock（[companion.go](../../../internal/output/companion.go#L17-L66)，[manager.go](../../../internal/worker/manager.go#L507-L537)）。 | 当前 companion 不满足用户指定的 final-only 多消息体验。必须实现 lexer/segmenter parity、delay 注入、配置接线并完成 L2/L4。 |
| B-03 | **companion 无可靠的可见发送/取消/故障语义。**无 DeliverySlot/Handle/TerminalArbiter；无命令 handler。`SendBatchText` 的普通 error 直接中断后续段（[manager.go](../../../internal/worker/manager.go#L525-L546)），不能区分 rejected/unknown/429，也不能在 successful terminal 后阻止首段。 | `/cancel`/`/new`、429、网络不确定和 shutdown 可能造成违反设计的继续发送、重复风险或不可解释的失败。必须落实线性化 slot、typed outcome、一次 429 retry、unknown stop、控制等待 done。 |
| B-04 | **本机 companion 交付事实与重启收尾缺失。**HLD/S04 要求每段 `server.log.wf` JSONL、digest/trace/batch 关联和 abandoned reconciliation；目前无 writer/事件，`.wf` 文件为空，server 启动也无 reconciliation。storage 只提供三种基本 transaction（[messages.go](../../../internal/storage/messages.go#L162-L231)）。 | 无法安全判断已可见的段、DB failure 后是否重发、或 restart 后是否应标为 abandoned。必须实现 workflow trace、transaction-only retry、restart reconciliation 与相应集成测试。 |

## 6. 建议的复审后整改顺序

1. 先由用户/设计确认：坚持 CardKit 主路径，或将真实、已验证的 PATCH 路径正式定为 S04 主路径；随后同步 S04/HLD（包括已裁定 UI 顺序）。
2. 若坚持既有 Story：补 CardKit adapter/operation ledger/L3，然后补 work 的 limiter、size/fallback 与可观测 outbound outcome。
3. 完整实现 companion：专属 final accumulator、lexer/segmenter parity、delay、typed sender outcome、DeliverySlot/Arbiter、transaction retry、workflow trace、reconciliation。
4. 为 B-01 至 B-04 编写先失败的测试，补 fake Feishu + fake clock + DB transaction/restart 集成测试；随后重跑全部 DoD gate。
5. 启动新 binary 后以**新 PID 之后**的唯一 work trace 和 companion trace 做 L4，保存无正文的 card/message/turn/batch/DB/trace 关联证据，再发起 blocker-only 复审。

## 7. 发布决定

当前服务可以继续作为“已验证 PATCH 双区 work UI 的本地测试实例”运行；它不应标记为 S04 Delivered 或 Ready for final validation，也不应把本次 UI 成功作为 companion/终态一致性/可恢复性已交付的证据。
