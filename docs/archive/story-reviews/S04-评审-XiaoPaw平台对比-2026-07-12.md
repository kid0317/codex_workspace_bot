# S04 设计独立评审：与 XiaoPaw Platform 的技术对比

> **评审对象**：[S04：双区流式卡片展示](../../story/S04-双区流式卡片展示-设计.md)（Ready）及 [HLD v3.8](../../02-redesign-high-level.md)
>
> **对比对象**：`/root/course/ai-pm/平台开发/xiaopaw-platform` 当前工作区的 S06/S07 设计与实现。
>
> **评审边界**：只读设计/源码评审；没有运行 XiaoPaw 服务、真实飞书或本项目的未实现 S04。本报告不把“本地单进程 + MySQL/内存队列”的本项目范围，与 XiaoPaw 的“多实例编排 + Redis + FC sandbox + 积分”的产品边界差异当成缺陷。

## 1. 结论

S04 的 work-mode 设计可作为实现基线：它比 XiaoPaw 当前 S07 的“整卡 PATCH + delta/process_delta”展示链路更严格地区分了 App Server 已完成的 `agentMessage`、展示白名单、同卡 sequence/未知结果和终态 drain。companion 的 final-only 方向也与本项目已裁定的产品模式一致。

但在开始编码前，建议先消除以下 **3 个 P1 契约缺口**：

1. companion 多段文本在“已部分发送、进程/存储失败”时没有可执行的恢复/放弃语义；
2. 一个 Batch 合并多条入站消息时，分段交付事实到底归属哪一条 `trace_id` 未定义；
3. Terminal 之后的 companion 发送阶段与 `/cancel`、`/new` 控制面缺少一个可实现的同一 Worker 状态/取消接口。

这三项不是 XiaoPaw 的产品需求移植，而是 S04 已承诺的“可追踪多段交付、取消停止余段、同 key 串行”本身所需要的闭环。建议修订后再进入实现；其余发现为 P2，可与实现设计一并收口。

## 3. 可复用实践与合理差异

### 可复用实践

1. **终态与状态写入相互校验**：XiaoPaw 在 Adapter 流正常结束但未见 `turn_completed` 时明确失败（`internal/sandboxapi/service.go:299-314`）。S04 的 `Terminal` drain 已具备相同方向；实现中应保持“Terminal 消费完且 companion delivery 已按既定策略收尾”后才释放同 channel Worker。
2. **外部 Feishu 边界使用 fake server 做可观测断言**：XiaoPaw 的 smoke 不只检查最终字符串，而检查 fake Feishu 调用和 MySQL/trace 结果（`tests/smoke_s07_stream_card_local_docker.py:296-356`）。S04 的 L2/LI-02 应采用同样方式，特别是断言 Terminal 前调用数为零、segment 顺序和失败重试次数。
3. **分层状态事实**：XiaoPaw 的 `feishu_event_logs` 有 processing lease、error code 和完成信息（`internal/storage/mysql/feishu_event_log_repository.go:248-345`）。本项目无需增加 Redis/lease，但可沿用“每个可恢复或不可恢复边界都有稳定错误码、条件状态迁移”的实践。
4. **飞书调用的明确超时与错误分类**：XiaoPaw card client 统一设置 timeout、重试和结构化依赖日志（`internal/feishu/card/client.go:249-270`）。S04 已给出 5/10 秒约束，实施时应将“限流”“明确失败”“响应不确定”映射为可测试的 typed outcome，而不能只依赖错误字符串。

### 合理差异，不构成缺陷

- XiaoPaw 的 Redis queue、租约、orphan reclaim、sandbox session 和积分结算服务于 FC/多实例生产编排；本项目的设计契约明确为 MySQL + 进程内 channel Worker，不能因此要求 S04 引入 Redis。
- XiaoPaw S07 公开的是 `delta/process_delta` 与最终答案的较粗粒度 SSE；S04 依据本机真实 App Server raw event 选择 completed `agentMessage` phase，避免把 reasoning/tool/raw 展示给用户。这是更严谨的展示收口，不是缺失流式能力。
- XiaoPaw 的卡片是整卡 PATCH；S04 预检 CardKit JSON 2.0 后以组件更新为主、PATCH 为降级。两者都需真实飞书验证，S04 的 L3/L3b/L4 硬门足够合理。

## 4. 发现与建议

### XP-S04-01 — P1：多段发送后的崩溃/存储失败没有可执行的交付恢复语义

**证据**

- S04 要求逐段发送、部分失败继续、只把首成功 message ID 和摘要错误码写 MySQL，并明确“不新增 segment 明细表”（S04:128-131,183-186）。
- 当前每条 Message 只保存一个 `feishu_bot_message_id`，没有 segment cursor/outbox（`migrations/001_initial.sql:30-48`）；旧 `CompleteBatch` 是在发送后逐条把 `processing` 改为 `succeeded`（`internal/storage/messages.go:143-153`）。
- S04 同时沿用“整体重启不恢复活跃 Turn”（S04:35-36）。

**风险**

若第 1/3 段已被飞书接受、进程在第 2 段或 `CompleteBatch` 前退出，重启后没有持久化 cursor 能判断哪些段已送达。此时若重新发送会重复已送达文本；若一律不重试则剩余段永久丢失，且 Message 可能停在 `processing`。这不是要求 exactly-once（飞书文本 API 的未知响应本来也无法保证），而是当前设计尚未选择“发生该故障时对用户和数据怎么诚实收尾”。

**建议**

在 Story 中二选一并写成状态机、错误码和测试：

- **A（推荐给个人本地应用）**：明确 at-most-one delivery attempt。进程重启/DB 完成失败后不自动重发 final；reconciler 只将请求置为 `failed` 或 `succeeded + companion_delivery_abandoned`，保留“可能已部分可见”的安全说明与 trace。新增 fake 测试：第 k 段成功后进程取消、以及全部段成功但 `CompleteBatch` 失败。
- **B（需要更强送达保证）**：新增最小 delivery outbox/segment 表，以 `batch_id + segment_index` 保存已确认进度，恢复时按 cursor 重试未确认段；接受仍可能重复当前未知 HTTP 结果的 at-least-once 语义。

**是否需要用户裁定：是。** 这决定是否接受“极少见故障下不自动补发”与是否扩展 schema。

### XP-S04-02 — P1：Batch 含多条 Message 时，companion 逐段 trace 的归属不明确

**证据**

- Worker `Batch` 包含多条 `Message`，每条都有独立 `TraceID`（`internal/worker/manager.go:46-59`）；S02 的既有契约也明确 Batch 有多个 Trace ID（`docs/story/S02-Worker队列与流式卡片-设计.md:145-163`）。
- S04 规定所有 segment 事实由“同一 trace ID”查询（S04:129,186,245），但没有定义 `batch_trace_id`、选择哪一条 Message trace，或如何向 Batch 内所有请求复制交付事件。

**风险**

LI-02 无法可靠地按“trace”拉出完整分段时间线；多条入站 Message 的查询会显示同一个 final/不同交付事实，或者只能看到首条 Message。后续排障会把批次输出误归属到某一用户请求。

**建议**

定义一个不改变原有每 Message trace 语义的聚合键：`batch_id` 为 companion delivery 的主关联键；每条结构化事件同时写 `batch_id`、`source_trace_ids`、`segment_index`、`turn_id`。若仍要求按单条 trace 查询，必须明确“向 Batch 内每一个 trace fan-out 同一 delivery event”或选择一个 deterministic primary trace，并在 MySQL/LI 查询中说明。相应增加一个多 Message Batch 的 L2/L4 查询断言。

**是否需要用户裁定：建议裁定。** 推荐 `batch_id + source_trace_ids`，避免把任何一条用户消息误当成整批的唯一 owner。

### XP-S04-03 — P1：Terminal 后 companion delivery 与 `/cancel`、`/new` 的控制面边界不完整

**证据**

- S04 要求 `/cancel`、`/new`、Worker stop 取消 delivery context 并停止未发送段（S04:128），但 HLD 对 `/cancel` 的定义仍是中断“当前 turn”（HLD:74-76,312-328）。
- S04 又要求 successful Terminal 后才开始 delivery，并等待 delivery ack 才释放 Worker（S04:155-157）。
- 当前 Worker 只有 `InProcess`/`Stopping` 等状态与 worker-wide `stop`，没有暴露 batch-owned delivery cancel handle（`internal/worker/manager.go:167-178,362-449`）。

**风险**

Turn 已终态时若实现已清除 `activeTurnID`，`/cancel` 可能被视为 no-op，后续文本仍在 400ms 延迟后继续发出；`/new` 也可能在旧 final 还在发送时创建/释放新 Thread。这会违背 S04 明确的“停止未发送段”和同 channel 串行。

**建议**

将 Worker 状态显式扩为 `DeliveringCompanion`（仍属于该 Batch 的 InProcess），存放 `{batch_id, turn_id, delivery_cancel, next_segment_index}`，并规定：

- `/cancel`/`/stop`：若 active turn 存在则 interrupt；若处于 delivery 则调用同一个 Worker-owned cancel，等待 sender 不再发新段后再回执；
- `/new`：先取消/await delivery，再 archive/clear Thread；不得让新 batch 与旧段交叉；
- worker timeout/Close：取消 delivery，并把未尝试段的摘要写入规定的最终状态；
- L2 使用 fake clock/blocked sender 覆盖“delay 中 cancel”“HTTP 请求中 cancel”“Terminal 与 `/new` 竞争”三种场景。

**是否需要用户裁定：否。** 这是已有 `/cancel`/`/new` 承诺的实现细化；推荐按上述规则收口。

### XP-S04-04 — P2：streaming 配置已在 HLD 出现，但实施接口、边界和 deterministic test 仍应前置

**证据**

- HLD 已有 `streaming.companion_segment_delay_ms: 400`（`docs/02-redesign-high-level.md:661-667`），S04 依赖该值和首/后续随机延迟窗口（S04:127）。
- 当前实现的 `Config` 和 `config.yaml.template` 没有 `Streaming` 配置对象或这个字段（`internal/config/config.go:13-35,74-126`; `config.yaml.template:1-26`）。

**风险**

若实现阶段临时使用常量，LI-02 的“符合配置的延迟”不可复现；若随机抖动直接读真实时钟，AT-11/12 可能变为易碎测试。

**建议**

实现设计中明确 `StreamingConfig` 的默认 400ms、可接受上下界、随机源注入方式、配置热更新与否（建议仅启动时读取），并增加 config validation/default unit test 和 fake clock/seeded RNG 的 sender test。无需改变产品范围。

**是否需要用户裁定：否。**

### XP-S04-05 — P2：逐段结构化 trace 的落点和 digest 算法需具体化

**证据**

- S04 要求写 `{index, text_digest, message_id|null, final_result}`，但只写“可由 trace ID 关联的结构化 trace”，未指定 sink、事件名或 digest 算法（S04:129,141,245）。
- HLD 规定 Langfuse 是 metadata-only、而本机 JSON workflow log 可持久化（HLD:711-768）。

**风险**

不同实现者可能把文本、弱摘要或 message ID 写入不同日志/外部观测面，导致 LI-02 无法稳定查询，也可能偏离 metadata-only 边界。

**建议**

定义唯一必达的本地结构化事件，例如 workflow JSONL `event=companion_segment_delivery`，字段至少为 `batch_id/trace_id(s)/thread_id/turn_id/segment_index/text_sha256/message_id/result/retry_count/at`；Langfuse 只 best-effort 复制无正文元数据。约定 SHA-256(UTF-8 segment) 小写 hex，禁止记录 segment 原文；为 writer failure 指定与 XP-S04-01 一致的处理策略。增加 fake logger 的字段/顺序断言。

**是否需要用户裁定：否。**

## 6. 未证实项与实施硬门

- 尚未实测飞书 CardKit 2.0 的 entity 发送、同 UUID 不确定响应重试、组件更新、settings 关闭；S04 L3/L3b/L4 仍是 Delivered 硬门，不能由 XiaoPaw 的 `Message.Patch` 实现替代。
- 未对 `/root/cc_workspace_bot` 的实际 sender 在网络未知响应/进程退出场景做运行实验；本报告只比较 S04 提出的兼容契约和 XiaoPaw 的队列/状态实践。
- 未验证本项目未来的 Langfuse 实现是否提供可查询的逐段 trace；当前工作区尚无 `internal/observability` 包，故不能把 Langfuse 当作 XP-S04-05 的唯一证据源。
- 未运行真实飞书、MySQL 或任何集成测试；本报告是设计审查，不构成 Delivered 证据。
