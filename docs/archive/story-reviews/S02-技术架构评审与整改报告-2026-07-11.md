# S02 技术架构独立评审与整改报告

> **评审角色**：独立技术架构师  
> **评审对象**：[S02 Worker 队列与流式卡片设计](../../story/S02-Worker队列与流式卡片-设计.md) 初稿  
> **日期**：2026-07-11  
> **初始结论**：不可从 Draft 直接进入 Ready；先完成下列阻塞整改并复核。

## 1. 独立问题汇总

### 阻塞

| ID | 问题 | 风险 |
|---|---|---|
| B1 | 初稿的“预留 → 解锁发卡 → 记录任务 → 唤醒”允许并发 Accept 因卡片 API 快慢而乱序，也可能留下永不释放的预留。 | 同 Chat 的 query 和卡片不再 FIFO，容量泄漏。 |
| B2 | 20 个 Worker 且永不回收，与 HLD/项目默认 30 分钟空闲回收冲突。 | 曾出现 20 个 Chat 后，服务永久拒绝新 Chat。 |
| B3 | 当前 S01 `router.App` 只有 ID/Name，无法向 job 可靠传递 workspace/model/effort/mode。 | 同群多 App 可能错误继承配置，未来 App Server 参数不可信。 |
| B4 | 初稿称 card message ID 仅在内存，但又要求 MySQL 验证出站 ID。 | 无法审计用户看到的卡片，也无法明确 fallback 覆盖规则。 |
| B5 | 初稿对所有 App 强制 interactive card，遗漏 `workspace_mode=companion` 的既有 plain-text 合约。 | 已配置 companion App 行为回归。 |

### 重要

| ID | 问题 | 风险 |
|---|---|---|
| M1 | Future App Server plan 没有 ChatGroup/已有 Thread/动作，`Input []string` 也不是明确的 text input 契约。 | 后续实现会重新猜测 start/resume/turn 参数。 |
| M2 | “handler 不等 5 秒”没有解决它仍等待最长 15 秒 card create 的问题。 | 飞书 ingress 快速接管边界不成立。 |
| M3 | S02 增加 processing 后，现有无条件完成/失败更新会允许晚到 finalize 覆盖终态。 | Message 状态和出站 ID 错乱。 |
| M4 | AT-02 的“drain 前三条均入队”依赖 goroutine 调度。 | 并发测试偶发、不证明批边界。 |
| M5 | 同群双 App 的真实飞书投递数未定义。 | L4 操作不可重复或被误判。 |
| M6 | `router`、`worker`、`feishu/output` 接线和每 App 凭据绑定不够明确。 | 实现可能继续走 S01 固定回复或使用错误 sender。 |

### Future

- 原 Message trace 与未来 batch/turn trace 只能做关联，不能误认为一个 JSON-RPC 请求 trace。
- 64 张卡片的顺序 final update 可在后续输出可靠性 Story 考虑限速/并行窗口；本期保持严格顺序。
- 卡片重试、幂等 update、崩溃恢复属于后续输出可靠性/恢复 Story。

## 2. 采纳决议与整改

| 问题 | 决议 | 已回写位置 |
|---|---|---|
| B1、M2、M4 | **采纳**：入队时在锁内写入带单调 FIFO 序号的 `card_pending` task；卡片创建由 Worker 输出阶段以 2 秒 deadline 异步完成。consumer 仅能 drain 从队首开始、已决议的连续 task。 | S02 §5、§6.1、§6.3、§7 AT-02/03/13 |
| B2 | **采纳**：实现/验收 30 分钟空闲回收；只允许 queue 空、无 batch、无 card pending 时条件删除 registry 并停止 goroutine。 | S02 §3、§5、§6.1、§7 AT-09 |
| B3、M6 | **采纳**：新增不可变 `AppRuntime`，由 `cmd/server` 每 App 创建；Router 入站与 job 复制完整 runtime；每个 runtime 绑定其 own Feishu output adapter。 | S02 §6.2、§6.3、§6.5、§7 AT-06 |
| B4、M3 | **采纳**：`messages.feishu_bot_message_id` 定义为该用户轮次首个可见出站消息；成功创建 card 立即条件写入；fallback 写入 text ID；状态转换均为条件更新。 | S02 §6.4、§7 AT-11/12 |
| B5 | **采纳**：work mode 使用 interactive card；companion mode 发送 plain text queued/processing/completed，本期不分段且不使用 `[[SEND]]`。 | S02 §3、§6.4、§6.5、§7 AT-07 |
| M1 | **采纳**：将 Future plan 改为显式内部 `ThreadPlan`、`TurnPlan`、`TextInputItem`，定义合并规则及 trace 关联边界。 | S02 §6.3、§7 AT-14 |
| M5 | **采纳**：L4 分为单 App 群的 batch 验证和预先记录事件投递数的双 App 同群隔离验证。 | S02 §8 |
