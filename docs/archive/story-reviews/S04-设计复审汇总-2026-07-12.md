# S04 设计复审汇总

> **评审对象**：[S04 双区流式卡片展示](../../story/S04-双区流式卡片展示-设计.md)
> **结论**：Ready，可进入实现；真实 CardKit L3/L4 仍是 Delivered 的硬门。

## 评审输入

- 用户裁定：只展示 `item/completed.agentMessage`；`commentary` 进入进展区，`final_answer` 进入正文区。
- S03 修复后的真实 L4：4 条 commentary 与 1 条 final answer，且混有必须拒绝展示的其它 Item 类型。
- 飞书官方 CardKit JSON 2.0 / streaming OpenAPI 与当前 Go SDK v3.9.9。

## 独立 UI/交互设计师结论

采用 CardKit JSON 2.0：正文置顶，初始“思考中…”，进展位于默认展开的折叠面板；`final_text` 与 `progress_text` 是独立 Markdown 组件。CardKit component text update 为主路径，现有同 message PATCH 是降级路径。流式期间不引入按钮。

## 技术 blocker 复审

初审发现两项 blocker，已整改并通过复审：

1. Card entity 发送成功但响应丢失时不能假设已有 `message_id`。现设计使用稳定 `open_uuid` 重试完全相同的发送；仍未知则 `SendUnconfirmed`，不创建第二张可见消息也不启动 Turn；明确未送达才切换 inline PATCH。
2. Runtime reader 到 Worker Projection 缺少有序终态交付。现设计定义 attempt-local `Bound`/`Item`/`Terminal` 管道、64 条有界 Item inbox、独立 Terminal control、drain ack 与 `StartTurn` 等待语义；reader 不等待飞书调用。

复审结论：PASS。

## 质量/安全 blocker 复审

初审发现四项 blocker，已整改并通过复审：

1. 展示 phase 改为 fail-closed：仅 `commentary`/`final_answer`；未知/缺失 phase 忽略。
2. agentMessage text 经 presentation sanitizer 后才成为 Markdown，飞书标签/HTML/`<at>`/`<link>` 不可执行。
3. CardKit 操作采用不可变 `pending_operation` ledger；未知结果重用同一 UUID、sequence、payload；终态按 progress → final → settings=false 顺序。
4. 每个序列化后的请求做字节检查；统一限速 CardKit 10/s、PATCH 5/s；过长最终文本以受上限保护的分段 text fallback 交付。

复审结论：PASS。

## Ready 边界

该结论只放行实现。CardKit 权限、稳定 UUID 重试、实体发送后同 message PATCH、组件更新和关闭流式模式必须在 S04 L3/L3b/L4 中真实验证；没有这些证据不得标记 Delivered。

## 2026-07-12 模式分流补充

用户补充裁定：上述双区卡片仅适用于任务型（`work`）应用。陪伴型（`companion`）应用不发送占位卡、不展示 commentary 或其它中间事件；只在整个 Turn 成功结束后发送 `final_answer`，并兼容旧 `/root/cc_workspace_bot` 的 `[[SEND]]` 多消息、打字延迟、限流单次重试与逐段错误继续语义。

首轮 companion blocker-only 复审发现 1 个 blocker：现有 `CompleteBatch` 无条件将 Message 写为 `succeeded`，而单一 `feishu_bot_message_id` 无法表达后续分段失败。已整改：`status=succeeded` 明确只表示 Turn 成功；`CompleteBatch` 接收 delivery summary，在同一条件迁移中将部分/全部未送达写为 `companion_segment_delivery_partial` / `companion_segment_delivery_none`，MySQL 只保存首成功 ID，全部分段结果由 trace ID 关联的结构化 trace 保存。Story 同时明确 delivery 使用 Worker-owned context，避免 Terminal 结束 turn context 后丢失交付。

整改复审再发现 marker-only final 的零分段边界：`[[SEND]][[SEND]]` 不得以 `succeeded + NULL error_code` 静默结束。已定义 usable final 必须至少有一段；零段改走单条安全文案、保存该消息 ID、`error_code=companion_final_empty`，不进入 normal segment completion。

最终 companion blocker-only 复审：**PASS**。模式分流、成功 Terminal 前零出站、旧 bot 分段/延迟/重试/取消语义、delivery summary、MySQL 首成功 ID/error_code、逐段 trace，以及 marker-only 收尾均无新增 blocker。S04 维持 **Ready，可进入实现**；CardKit 的真实 L3/L3b/L4 和 companion 的真实 LI-02 仍是 Delivered 硬门。

## 模型不稳定 delimiter 兼容补充

用户进一步要求 companion 的发送语义兼容模型输出不稳定的 delimiter。S04 以 `CompanionDelimiterLexer` 补在旧 Segmenter 前：局部 NFKC/括号折叠/零宽清理后兼容双括号的空格、大小写和全角/方头变体；单括号只允许独立控制行；fenced code、非整行 inline code 与反斜杠转义保持字面文本。AT-14/15 与 LI-02 已覆盖。等待该正则/词法边界的独立 blocker-only 复审。

该 delimiter blocker-only 复审：**PASS**。internal token 成为旧 Segmenter 的唯一 delimiter；RE2 候选后手工校验配对 backtick；反斜杠奇偶与 `storage_text` 均有可验收契约；两个 RE2 已经 Go `regexp.Compile` 实测通过。S04 维持 **Ready，可进入实现**。
