# S04 评审：测试方案完整性

> **评审类型**：独立、只读的测试/验收方案审查
> **评审日期**：2026-07-12
> **范围**：S04 work CardKit 双区投影与 companion final-only/兼容 lexer/多消息交付；同时核对 S01–S03 的当前可执行测试、SOP 与恢复/持久化边界。
> **结论**：**有条件通过，尚不建议以当前测试设计直接进入实现。**S04 的正向功能、主要协议故障和真实 L3/L4 已比 S01–S03 的同阶段设计更具体；但 companion 的“外部已经可见而 MySQL 收尾失败”、发送结果不确定、重启中途交付、批量行收尾和逐段 trace 合同，仍缺少可执行且能防止重复发送的测试门禁。下表的 P1 项关闭后，测试方案才足以作为实现与 Delivered 判定的依据。

## 1. 审查方法与当前证据

- 阅读 [S04 Story](../../story/S04-双区流式卡片展示-设计.md)、[HLD](../../02-redesign-high-level.md)、[项目 AGENTS](../../../AGENTS.md) 与 [Story Delivery SOP](../../sop/story-design-to-delivery.md)。
- 审阅当前实现/测试边界：`internal/codexapp/*_test.go`、`internal/worker/*_test.go`、`internal/storage/*_test.go`；复核 S02、S03 Delivered 复盘中已发生的 PATCH、状态机、L3/L4 证据问题。
- 以只读方式于本工作树执行：`go test ./... -count=1`、`go vet ./...`、`go test -race ./internal/codexapp ./internal/worker ./internal/storage -count=1`，均以 exit 0 结束。

这不是 S04 已实现的证据：当前 `worker.Output` 只有 `CreateBatchCard` / `UpdateBatchCard` / 单次 `SendBatchText`（[manager.go](../../../internal/worker/manager.go:69)），现有 companion 仍在 processor 成功后发送固定“本轮已完成。”（[manager.go](../../../internal/worker/manager.go:362)）。当前 `CompleteBatch` 也只收一个 bot message ID 与文本（[messages.go](../../../internal/storage/messages.go:143)）。因此现有绿测证明的是 S01–S03 基线，不能证明 S04 的 CardKit、DisplayEvent、lexer、multi-send 或交付摘要。

## 4. 不应误用的测试证据

1. `go test ./...`、`go vet ./...` 与现有 race 测试为绿，**不等于** S04 已有覆盖；目前没有 `output`/CardKit/lexer 包及对应测试，现有 companion 测试只验证固定文本路径（[manager_test.go](../../../internal/worker/manager_test.go:255)）。
2. fake CardKit/PATCH 成功只证明本地序列与 payload；不能替代 L3b 的真实 SDK/权限/稳定 UUID 重试，也不能替代 L4 的“同一飞书 message ID 用户可见更新”。这正是 S02 曾因使用错误 Update API 而失败的类别。
3. 单条成功 companion L4 不能证明 lexer 的全体变体、rate limit、unknown send、cancel、DB failure 或 restart。它们必须有 deterministic fake sender/storage/clock 的 L1/L2 覆盖。
4. App Server raw/event/outcome 的完整性不能证明 presentation sink 已消费、Terminal drain 已完成，或每段 delivery trace 已写；需要独立 display/delivery observer 断言。
5. `go test -race` 没有 panic 只能发现数据竞争的一部分；必须在测试内断言 sequence 单调、每个 Item/Terminal 只消费一次、next Batch 未越过 delivery barrier 和 goroutine 收敛。
6. 旧 CC Workspace Bot 的 `segment_test.go` 可作为语义样本，不能当作新 bot 的绿测；旧 repo 在当前主机 Go 1.23 下不满足其 Go ≥1.24 要求，且不包含 S04 的 lexer、MySQL、CardKit 或终态投递时机。

## 5. 建议的测试分层与放行顺序

1. **先补 L1/L2 的 P1 用例**：T1–T7，使用 fake App Server、fake CardKit/PATCH/sender、fake storage、fake observer、fake clock 与可控 RNG；每个外部调用应有 request count 和 call order 断言。
2. **再补确定性语义回归**：T8–T11，尤其是 lexer+Segmenter 的组合 golden、trace schema 和安全文案失败路径。
3. **实现批次门禁**：`gofmt`、`go vet ./...`、`go test ./... -count=1`、`go test -race ./... -count=20`，另将 `codexapp`/`worker`/`storage`/新增 `output` 的高并发 targeted race 提升到 `-count=50`。真实 App Server、CardKit/Feishu 都保留为显式环境变量 gate，绝不混入默认单测。
4. **外部 L3/L4 放行**：先 L3b CardKit preflight；随后以新进程/新 trace 完成 work 与 companion 两组 L4，收集 process start、配置/SDK 指纹、message/card IDs、MySQL 行、event/outcome/delivery trace、最终截图。失败/降级样本不得被成功样本替代。

## 6. 总体结论

S04 已经具备可实现的测试骨架，且 work/companion 的产品边界、失败注入和实证意识明显优于仅以 happy path 验收的设计。要使该骨架真正防止用户最关心的“多消息送达不重不漏”，需要先关闭 T1–T7：尤其是将飞书可见副作用与 MySQL 收尾拆开测试、定义不确定发送与重启的安全策略、并让逐段 trace 成为可检验合同。T3 是唯一需要产品取舍的事项；其余可按报告中的保守默认直接回写为 S04 的 AT/DoD。
