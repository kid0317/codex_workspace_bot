# S04 P1 设计修订 blocker-only 复审

> **对象**：[S04：双区流式卡片展示](../../story/S04-双区流式卡片展示-设计.md)、[HLD v4.0](../../02-redesign-high-level.md)
> **日期**：2026-07-12
> **性质**：独立、只读、blocker-only 复审；未修改 Story、HLD 或运行时代码。
> **结论**：**BLOCKED（3 个实现前 blocker）**。P1 已显著补齐 Terminal、批量事务、未知发送、trace 和测试边界；但下列缺口仍会导致“取消后仍可见发送”、背压不再有界，或重启时错误归类/无法关联 Batch。修订并补充相应 AT 后，可重新复审。

## 1. 审查范围与证据

本次只核验 P1 修订后的六个目标：

1. `TerminalArbiter` / `DeliveryHandle` 覆盖 completed、timeout、runtime exit、cancel、`/new` 与 delivery 的竞态；
2. Batch transaction、仅 DB retry 与 restart abandoned reconciliation 是否不造成可见重发；
3. `unknown`、明确拒绝和 429 的顺序/结果语义；
4. pre/post-bind cap 是否同时满足“有界 + reader 不阻塞”；
5. batch/source trace、workflow writer 失败、latest final、配置与 AT-17～AT-24 是否闭环。

静态证据包括：

- S04 §5、§6.3～§6.7、§7（[S04:65](../../story/S04-双区流式卡片展示-设计.md#L65)、[S04:125](../../story/S04-双区流式卡片展示-设计.md#L125)、[S04:156](../../story/S04-双区流式卡片展示-设计.md#L156)、[S04:221](../../story/S04-双区流式卡片展示-设计.md#L221)、[S04:254](../../story/S04-双区流式卡片展示-设计.md#L254)）；
- HLD companion/日志/配置契约（[HLD:374](../../02-redesign-high-level.md#L374)、[HLD:667](../../02-redesign-high-level.md#L667)、[HLD:772](../../02-redesign-high-level.md#L772)）；
- 旧 CC Workspace Bot 的真实分段/延迟/429/普通错误继续实现（`/root/cc_workspace_bot/internal/session/segment.go:53-86,257-305`、`worker.go:334-379`）；
- 当前存储基线只有 Message 行状态，无已持久化 Batch 或 delivery-stage 字段（`internal/storage/messages.go:130-174`）。

本轮没有把当前 S01–S03 代码测试当成 S04 验收证据。

## 2. 已确认闭环的部分

- **可见重复控制**：未知 SendText 不重试、DB retry 只重试 transaction、重启不续发，方向正确；`sent/rejected/unknown/cancelled` 的终态类型、首成功 message ID 与不可变 ledger 已明确。
- **明确拒绝与 429 的基本顺序**：明确 rejected 按旧 bot 语义记录后继续；429 只在同段退避 500ms 后重试一次；unknown 停止余段，避免在不确定已可见时继续打乱用户顺序。
- **latest final 与 trace 内容边界**：同 `item.id` 去重、latest non-empty wins、Terminal 后拒绝 Item；workflow trace 有 batch/source traces、turn、index、digest，且不写正文。
- **writer 失败与测试意图**：workflow writer 失败停止未发送段，Langfuse fail-open；AT-19～AT-24 已覆盖多 final、transaction、未知发送、writer、multi-trace 和 fake clock/RNG。

这些都应在 blocker 修订中保留，不应退回到旧的“发送后尽力记录”或“DB 失败重发飞书”模式。

## 3. Blockers

### B1 — 成功 Terminal 到 `DeliveryHandle` 发布之间存在取消穿透窗口

**证据**：S04 将 control CAS 限定为 `Active → Stopping`，completed 则从 `Active` 直接进入成功 Terminal（[S04:170-175](../../story/S04-双区流式卡片展示-设计.md#L170)）。它只规定“若已进入 Delivering 则取消 Handle”（[S04:172](../../story/S04-双区流式卡片展示-设计.md#L172)），而 companion 仅在 drain 之后才“创建 `DeliveryHandle` 并发送”（[S04:177](../../story/S04-双区流式卡片展示-设计.md#L177)）。`/new`/`/cancel` 的等待规则也只覆盖已在 Delivering 的 handle（[S04:229-230](../../story/S04-双区流式卡片展示-设计.md#L229)）。

**失败交错**：

1. `turn/completed=completed` 先 CAS 成功，attempt 进入 Terminal/Draining；
2. `/cancel` 或 `/new` 到达，此时已不是 `Active`、但 `DeliveryHandle` 尚未发布；命令既不能 CAS 为 `Stopping`，也没有可取消的 handle；
3. 命令路径继续清理/返回，随后 worker 创建 handle 并发送 first segment。

这违反“控制面取消优先”及 AT-17 的“cancel/new 在首段 delay、SendText、429 retry 中都取消 delivery”。Worker shutdown 也有同一窗口。仅在 handle 已经存在时加 mutex 不足以消除它。

**必须回写的最小契约**：

- 定义 attempt-owned、先于任何成功 Terminal 创建的 `delivery_slot`（含 `cancel_requested` latch、`published`、`done`）；
- `BeginDelivery` 与 control command 使用同一个线性化锁/原子状态：只有在锁内确认“成功 Terminal 且没有 cancel/stop latch”后才能发布 handle/开始首段 delay；
- control 能在 `Terminal`、`Draining`、`Delivering` 任意尚未 `Drained` 的状态置 latch；若 handle 未发布，它等待/观察 slot 关闭而不是提前 archive 或释放 Worker；若已发布，取消其 context 并等 `done`；
- 将“控制面优先”从不可能的无条件抢占改为可测试的线性化规则：control 在 `BeginDelivery` 前取得锁必然阻止可见发送；`BeginDelivery` 先取得锁后，control 只允许取消尚未完成的 delay/API/retry，已获响应段不撤回。

**验收补充**：AT-17 必须加入上述精确交错（successful Terminal 已裁决、handle 尚未发布、再 cancel/new/shutdown），断言 `SendText=0`、archive/下一 Batch 在 slot `done` 后发生；另加 BeginDelivery 已发布后的反向交错。

### B2 — post-bind 只有条目数 cap，没有字节 cap，不能证明展示管道有界

**证据**：设计决策说 pre-bind 与 post-bind 都有“事件/字节上限”（[S04:67](../../story/S04-双区流式卡片展示-设计.md#L67)）。但 pre-bind 才有“64 条 + 256 KiB”（[S04:166](../../story/S04-双区流式卡片展示-设计.md#L166)）；post-bind 只规定普通 Item inbox 为 64 条并在第 65 条失败（[S04:168](../../story/S04-双区流式卡片展示-设计.md#L168)）。AT-18 同样只覆盖 post-bind 第 65 条，而未覆盖单个/64 个超大 item（[S04:256](../../story/S04-双区流式卡片展示-设计.md#L256)）。

因此 64 个任意大的 `sanitized_text` 仍可被 reader 接受；这不是 bounded memory，也没有说明单个大 Item 应在何处、以何种非阻塞方式失败。高频/大 final 时，P1-4 所要解决的“reader 不阻塞且有界”矛盾仍存在。

**必须回写的最小契约**：

- post-bind inbox 采用同时按 `count` 与**序列化后字节数**计量的 reservation（推荐同 pre-bind 64 / 256 KiB，或明确不同常量）；单个 Item 超过可用 byte budget 也必须立即失败；
- `TryPublish` 在 reader 内以非阻塞方式原子 reserve count+bytes；pump 消费后释放同一实际字节数，不能仅依 channel length；
- 失败路径仍只投递容量为 1 的 Terminal control，并保留 S03 raw/event/outcome；不得把超限文本先复制进 Projection/final accumulator；
- 明确 bytes 在 sanitizer 后、构造 `DisplayEvent` 前计算，防止原始 payload/重复副本绕开预算。

**验收补充**：AT-18 增加：单一 256KiB+1 item、64 个合计超 budget 的 item、pump 并发释放时的 reservation race；均断言 reader 无阻塞、无大文本进入 output state、仅一个 `presentation_backpressure` Terminal。

### B3 — abandoned reconciliation 缺少持久化的 delivery-stage 与 Batch 身份，无法安全选中或关联遗留行

**证据**：S04 要求 restart 后把“遗留 `processing` Message”标为 `companion_delivery_abandoned`（[S04:136](../../story/S04-双区流式卡片展示-设计.md#L136)、[S04:140](../../story/S04-双区流式卡片展示-设计.md#L140)），并要求 `batch_id` 成为主关联键、每条 trace 有完整 `source_trace_ids`（[S04:68](../../story/S04-双区流式卡片展示-设计.md#L68)、[S04:135](../../story/S04-双区流式卡片展示-设计.md#L135)）。但当前/设计中的 `messages` 只有逐条状态与 `error_code`，没有 `batch_id`、delivery-stage 或 delivery-start marker；S04 又明确不新增 segment table/JSON 字段（[S04:136](../../story/S04-双区流式卡片展示-设计.md#L136)、[S04:206](../../story/S04-双区流式卡片展示-设计.md#L206)）。

新进程因此不能仅凭 `status=processing` 区分：

- work mode 或尚在 App Server Turn 的 processing Message；
- companion 但尚未进入可见 delivery 的 Message；
- 已进入 delivery、可能已有部分段可见的 Message；
- 属于同一个多 Message Batch 的哪些行，以及它原来的 `batch_id`。

将全部 processing 行标为 abandoned 会误覆盖 S03 的 `app_server_exited`/普通失败分类；新生成 batch ID 又无法与已写 workflow trace 关联。这与“按 batch/source trace 查询”和 AT-16/AT-23 的证据承诺相矛盾。

**必须回写的最小契约（不等于引入 segment ledger/outbox）**：

- 在**第一条可能可见的 SendText 之前**，以单个 transaction 为该 Batch 的全部 processing Message 持久化同一个不可变 `companion_delivery_batch_id` 和 `delivery_stage=companion_delivery_started`（可使用最小新增列；不记录 segment cursor/已发送段，不构成 outbox）；
- 启动 reconciliation 的条件必须是 `status=processing AND delivery_stage=companion_delivery_started`，按该 batch id 关联所有 source Message，并只改这些行；work/未进入 delivery 的 companion 行走既有 runtime-exit 收尾，绝不能被误标 abandoned；
- abandoned trace 复用持久化的原 batch ID/source traces，不能临时生成一个无关联 ID；transaction 成功 finalization 必须清除/收束 delivery_stage；
- 若坚持零 schema 变化，则必须明确等价的、可从已有持久化字段无歧义且稳定地导出 batch id/stage 的算法，并在 restart 前后保持完全一致；当前文档未给出这种算法。

**验收补充**：AT-16/AT-20/AT-23 增加同库混合 fixture：work processing、companion active-turn processing、两个 companion delivery Batch（其中一个部分发送）共同遗留。只允许被 marker 选中的 Batch 变 abandoned；每个 abandoned trace 用原 batch ID 和完整 source traces；不得产生 SendText。

## 4. 非 blocker 但应在同一回写中澄清

1. **429 trace 的语义**：S04 规定“每个 API result”都写 trace（[S04:135](../../story/S04-双区流式卡片展示-设计.md#L135)），但枚举没有 `rate_limited`，且“rejected 后继续”的规则会让第一次 429 与最终明确拒绝在 trace 中同为 `rejected`。建议明确：第一次 429 写 `result=rejected,retry_count=0,reason=rate_limited`，500ms 后第二次结果写 `retry_count=1`；第二次仍 429 作为明确拒绝并继续。`reason` 只允许稳定枚举、不得含 API 原文。这样 AT-21 才能既断言调用顺序，也能审计为什么发生 retry。
2. **配置落点**：HLD 给出了 `streaming.companion_segment_delay_ms=400` 与范围，但当前 `config.yaml.template`、`internal/config.Config` 尚无 `streaming` 节。它不是现在要改代码的 blocker，不过实现开始前应把 schema、默认值与启动校验一并加入，并将对应配置解析/非法值测试列入 AT-24。
3. **AT-19 的“work/companion 最终内容一致”**：若 fixture 含已识别 delimiter，companion 的 `storage_text` 会移除它，work 卡则按当前设计保留原 final 文本；不应作字节相等断言。建议把 AT-19 限定为同一 latest final Item 被选择，文本清洗差异由 AT-14/15 单独断言。

## 5. 复审结论与下一步

在 B1、B2、B3 回写前，本设计不能恢复 Ready：它们分别涉及用户可见取消语义、内存/reader 稳定性、以及“断掉就断掉但不误分类、不重发”的用户裁定。三处修订后，保留 AT-17～AT-24 并追加本报告所列交错/混合 fixture，即可发起下一轮 blocker-only 复审。

## 第二轮复审（B1–B3 回写后）

> **结论**：**BLOCKED（1 个最小 blocker）**。
>
> 第一轮的 B1 与 B2 已通过；B3 已补齐 batch/stage 的持久化与启动筛选，但“marker 已写入后，被控制面取消或本 generation 失败”的正常收尾还没有清除 marker 的明确存储契约。这会使未曾可见发送的 Batch 在下一次启动被误标为 `companion_delivery_abandoned`。

### 已通过的回写

1. **B1：通过。**`DeliverySlot` 在 attempt 创建时建立，并规定其状态、`BeginDelivery` 与 command 共用 Worker mutex；`done` 对“未发布即取消”和 Handle 收尾均恰好关闭一次。`BeginDelivery` 在 marker transaction 后重新取锁检查 cancel latch，故 control 在该线性化点先获锁时不会执行 `SendText`。S04 [170-177](../../story/S04-双区流式卡片展示-设计.md#L170)、[229-231](../../story/S04-双区流式卡片展示-设计.md#L229) 与 AT-17 已覆盖 handle 未发布/已发布的两侧交错。
2. **B2：通过。**post-bind 已明确为 64 条加 256 KiB 的 count+byte reservation；reservation 在 sanitizer 后、DisplayEvent 构造/复制前原子取得，pump 依实际 reservation 释放。AT-18 补上单一超大 item、总字节超限和并发释放 race。S04 [166-168](../../story/S04-双区流式卡片展示-设计.md#L166)、[256](../../story/S04-双区流式卡片展示-设计.md#L256)。
3. **B3 的持久化识别部分：通过。**HLD 定义了最小 `companion_delivery_batch_id`/`delivery_stage` 列及索引，`MarkCompanionDeliveryStarted` 在首条可见发送前原子写入；reconciliation 只选择这个 stage，并复用原 batch/source traces。S04 [134-140](../../story/S04-双区流式卡片展示-设计.md#L134)、[206](../../story/S04-双区流式卡片展示-设计.md#L206)，HLD [604-618](../../02-redesign-high-level.md#L604)、[392-396](../../02-redesign-high-level.md#L392)，AT-16/20/23 已覆盖混合遗留行、transaction 与关联。

### B4 — marker 已写入但未完成正常 delivery 的 control/failure 收尾未定义，可能被误标 abandoned

**证据**：`BeginDelivery` 的顺序是先把 batch/stage 写入 MySQL，再重新获得 mutex 才发布 Handle（S04 [134](../../story/S04-双区流式卡片展示-设计.md#L134)）。control 可在两步之间置 cancel latch，且此时禁止 `SendText`（S04 [172](../../story/S04-双区流式卡片展示-设计.md#L172)、[229-230](../../story/S04-双区流式卡片展示-设计.md#L229)）。但 storage 契约只说明 `CompleteBatch` 成功 transaction 清除 stage（S04 [136](../../story/S04-双区流式卡片展示-设计.md#L136)），reconciliation 才清除 abandoned stage（S04 [140](../../story/S04-双区流式卡片展示-设计.md#L140)）；没有定义 cancel、`BeginDelivery` abort、trace-writer failure 或其他 delivery failure 的**当前 generation**条件收尾和 stage 清除。

**失败交错**：

1. successful Terminal 进入 `DeliveryStarting`，`MarkCompanionDeliveryStarted` 成功；
2. `/cancel` 或 `/new` 在第二次 mutex 获取前置 latch；`BeginDelivery` 正确不发送、关闭 slot；
3. 若 Worker 的正常失败收尾没有按 batch/stage 条件清除 marker，Message 仍是 `processing + companion_delivery_started`；
4. 下一次启动把它视为“可能部分可见的 abandoned delivery”。这既错误覆盖了已取消（且可能零可见段）的真实原因，也破坏了 B3 “只将实际 delivery 遗留标 abandoned”的分类目标。

**最小修复**：在 storage 边界补充一个全量条件收尾（可命名 `FailCompanionDelivery`/`FinalizeCompanionDelivery`）：对同一 `batch_id + delivery_stage + status=processing` 的所有 source Message 使用一个 transaction，写明确的失败/取消安全码、`completed_at` 并清除 stage。所有 marker 已写入后的非成功分支都必须走它：

- control latch 在 Handle 发布前；
- 已发布 delivery 的 cancel/stop；
- workflow trace writer failure；
- delivery 侧本地失败。

只有此 transaction 最终失败、进程退出前无法收尾的 marker 行，才留给启动 reconciliation 标记 `companion_delivery_abandoned`；该 trace 可保留“可能部分可见”的事实。正常 `CompleteBatch`（含 rejected/unknown 等 summary）继续作为成功 Turn 的收尾路径并清除 stage，绝不重发飞书段。

**验收补充**：在 AT-16/AT-17/AT-20 增加“marker transaction 成功 → control 先获 DeliverySlot mutex → `SendText=0` → 同 generation conditional fail-finalize 成功”的 fixture，断言所有 source Message 不再是 processing、不带 stage，重启 reconciliation 不触及它；另断言 fail-finalize 的 transient/permanent DB failure 不会触发 SendText，只有未能收尾的行才在重启时 abandoned。

除 B4 外，本轮复核的 DeliverySlot 线性化、post-bind reservation、batch/source trace、429 reason、latest-final、workflow writer failure、`streaming` schema 与 AT-16～AT-24 已形成可实现的闭环。

## 第三轮复审（B4 回写后）

> **结论**：**PASS（设计可恢复 Ready，尚未代表实现或真实飞书验收通过）**。

### B4 验证结果

1. **marker 后的 current-generation 收尾已闭环。**S04 明确 `FailCompanionDelivery(ctx, batchID, errorCode, safeContent, duration)` 与 `CompleteBatch` 都以 `processing + batch_id + delivery_stage` 为条件，对整个 Batch 使用单一 transaction 收尾并清除 stage；DB retry 只重试该 transaction，绝不回到 `SendText`（[S04:136](../../story/S04-双区流式卡片展示-设计.md#L136)）。
2. **失败路径覆盖充分。**Handle 发布前的 control cancel、已发布后的 cancel/stop、workflow trace writer failure 以及其他本 generation delivery failure 都被要求进入 `FailCompanionDelivery`；slot 关闭前需等待其成功或记录最终 DB failure（[S04:136](../../story/S04-双区流式卡片展示-设计.md#L136)、[S04:229-232](../../story/S04-双区流式卡片展示-设计.md#L229)）。这消除了“零可见已取消 Batch 遗留 marker，重启后误标 abandoned”的路径。
3. **restart-abandoned 的选择已收紧。**只有 fail-finalize 最终无法完成且 generation 退出后仍遗留的 `processing + companion_delivery_started + batch_id` 行可被新 generation 选中；reconciliation 按原 batch ID 标 failed/abandoned、清除 stage、复用 source traces，且不得 `SendText`（[S04:140](../../story/S04-双区流式卡片展示-设计.md#L140)）。HLD 在 storage schema、current-generation finalize 与 restart 条件上保持同一契约（[HLD:392](../../02-redesign-high-level.md#L392)、[HLD:396](../../02-redesign-high-level.md#L396)、[HLD:618](../../02-redesign-high-level.md#L618)）。
4. **验收覆盖已对齐。**AT-16 限定 generation 退出且未收尾的 marker；AT-17 验证 marker 成功后 control 抢占时 `SendText=0` 且同 generation fail-finalize 清 stage；AT-20 覆盖 trace/local failure、两个 finalize 的 all-or-nothing、以及仅未能 fail-finalize 的行可 restart-abandoned（[S04:254-260](../../story/S04-双区流式卡片展示-设计.md#L254)）。

本轮未发现新的 blocker。该 PASS 仅表示 Story/HLD 的 B1–B4 设计契约互相一致、可进入实现准备；S04 仍需按 Definition of Done 实施 migration、配置、storage/worker/output 测试、race gate、CardKit L3/L3b 和真实飞书 L4 后，才能宣称 Delivered。
