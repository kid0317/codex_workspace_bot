# Story 1 独立评审：资深技术架构师

> **评审角色**: 资深 Go 系统架构师  
> **对象**: Story 1 设计、概要设计 v3、项目 AGENTS 约束  
> **结论**: **修改后批准实现（Approve with changes）**

## 审阅范围

聚焦领域边界、MySQL 约束与迁移幂等、并发/关闭、配置归属、Docker 可运维性、验收严谨性和 Story 范围；未深入复核 App Server 与飞书协议细节。

## Blocking

### B1：缺少 AllowedChats 持久化模型与入站授权门

**证据**：项目要求 App 以配置、凭证、工作目录和 allowed chat rules 隔离，且在入队前校验；现有 `apps`、`chat_groups`、`messages` 和 Story 均未建模该规则。

**风险**：机器人被拉入的任意群或可触达的任意单聊都会被持久化并回复；后续 `never + danger-full-access` 会暴露给未授权聊天。

**建议**：P0 新增 `app_allowed_chats(app_id, chat_type, chat_id, enabled, created_at, updated_at)`，唯一键 `(app_id, chat_type, chat_id)`；在创建 ChatGroup、Message 和投递前校验；`appctl` 管理该规则；未授权消息不落业务表、不回复，仅写脱敏日志。若允许全部聊天，必须由 App 级显式字段表达并经人工确认，不能隐式默认放行。

### B2：Message 的冗余 `app_id` 无法和 ChatGroup 的 App 一致

**证据**：`messages` 同时保存 `app_id` 与 `chat_group_id`，但两个外键均为单列，无法约束 `messages.app_id = chat_groups.app_id`。

**风险**：错误的 Repository 或维护脚本可生成跨 App 的消息，损坏查询、审计和 Langfuse 归属。

**建议**：优先移除 `messages.app_id`，通过 ChatGroup join 查询；若保留以优化查询，则新增 `chat_groups UNIQUE(app_id, id)` 及 `messages(app_id, chat_group_id)` 的复合外键。已产生审计数据的 App 仅允许 disable，物理 delete 只允许无关联数据。

## Major

1. **同渠道串行不应后置**：飞书 handler 可能并发，去重不保证两条不同消息顺序。P0 至少实现 `channel_key` 单 goroutine、有界队列的 dispatcher（建议全局 20、每队 64）；队满/池满创建 `rejected` Message 并返回确定性提示，绝不静默丢弃；测试同键顺序、异键并行和饱和。
2. **迁移需要执行器契约**：定义 `schema_migrations(version, checksum, applied_at)`、MySQL `GET_LOCK`、前向只增、checksum/锁超时/脏版本 fail-fast，以及空库、重复、并发 migrator、失败诊断测试。
3. **关闭语义缺失**：SIGTERM 后停止接收、有限时间 drain、未完成 Message 写 `shutdown_interrupted`，再关闭 receiver/worker/DB；明确重复事件如何重试或人工恢复。
4. **`appctl` Secret 输入会泄漏 argv/history**：禁止 `--secret` 明文 flag，使用 stdin、无回显交互输入或权限受限文件；list/show/error/log 默认均不得包含 Secret。
5. **一期模板混入未启用能力**：worker、codex、langfuse 参数要么移到未来示例，要么明确不生效；若保留 HTTP，定义本地 `/healthz` 的 200/非 200 依赖语义。

## Minor

- MySQL 8.4 对 mode、chat type、状态和策略增加 `CHECK`；状态转移使用条件更新。
- 固定回显不展示真实 `chat_id`，用本地 ChatGroup 短 ID/hash 与 `trace_id`。
- MySQL 镜像固定到 patch tag/digest，并检查宿主机挂载目录权限；“Docker 开机启动”是部署前置条件，非代码保证。
- 补充已有历史数据的 App delete、部分 receiver 启动失败、WebSocket 断线和 SIGTERM drain 的验收。

## 已验证的正向选择

- `apps → chat_groups → messages` 与 Worker 非持久化的边界清晰。
- 一轮一条 Message 与不可变 `trace_id` 是合理的 Langfuse 审计边界。
- YAML 进程配置、DB 应用配置的单一所有权正确。
- 短事务不等待飞书发送、localhost bind mount MySQL、真实飞书 smoke 与 fake 证据分级均合理。

## 判定

关闭 B1、B2，并把同渠道串行、迁移、关闭、Secret 输入和健康语义写入 Story 后，可开始实现。
