# S05 设计独立评审汇总（2026-07-12）

> **结论**：设计范围可接受；没有未整改的设计 blocker。2026-07-13 的真实 App Server L3 已证明 `dynamicTools` 在新 Thread 的 `thread/resume` 后仍可用，S05 可进入 **Ready**。

## 审阅范围

审阅对象为 [S05 设计](../../story/S05-附件输入与飞书能力代理-设计.md)，对照本项目 `AGENTS.md`、HLD、Story SOP、当前 Go 实现、XiaoPaw S11/S12 与旧 CC Workspace Bot 的附件/飞书能力实现。审阅不修改运行时代码、配置、数据库或外部飞书资源。

## 三个独立视角

| 视角 | 结论 | 已回写的关键设计 |
|---|---|---|
| 技术架构 | 无剩余 blocker | Client/Runtime 由“所有 server request 预拒绝”改为单一 router + 单一 writer；early `item/tool/call` 有界 pre-bind buffer；动作在 attempt-owned executor 中执行；旧 Thread toolset 迁移和 new Thread resume hard gate 明确。 |
| 质量/安全 | 无剩余 blocker | 附件是 Batch 合并边界；无效附件有失败 receipt；resource/action result 使用 AES-GCM keyring；外部动作使用复合 claim 状态机、lease cleanup 与安全文件对象校验。 |
| 产品架构 | 无 blocker；有三项已采纳的收口 | 统一到飞书安全上限 30,000,000 bytes；普通文件只承诺安全提供给 Codex 读取；doc 已创建而公告失败时必须诚实提示并保留 URL。 |

## 已整改的阻塞项

1. 当前 Worker 会把 drain 内消息合并，已定义“含 required attachment 的 Message 自成 Batch”的边界，防止附件失败误伤后续文本。
2. 当前 client/runtime 会在工具处理前预拒绝 server request，已定义 router、early request buffer、exact thread/turn bind 和唯一 response writer。
3. 当前 persisted Thread 没有 dynamic tool catalog，已定义 `codex_toolset_version` 和 archive/CAS/lazy new-thread 升级；新 Thread resume 不保留 catalog 时禁止进入 Ready。
4. 附件 resource key、外部动作结果和 duplicate call 原先缺少可恢复安全契约，现已定义 AEAD keyring、密文擦除、加密 result cache 与 `(app_id,thread_id,turn_id,call_id)` claim 状态机。
5. 路径校验、清理与实际 child namespace 原先不完整，现已定义 workspace-relative attachment root、fd-based `openat`/`O_NOFOLLOW`、attempt lease、重启收尾及真实 child L3 验证。
6. 文档创建原先可能只让模型看到 URL，现已定义创建后主动向当前 channel 公告，partial/announcement failure 仍保留诚实 URL 结果。

## Ready 硬门与实测证据

2026-07-13 使用 `codex app-server --stdio`（CLI `0.144.1`）完成：`initialize` → `thread/start(dynamicTools=[feishu.echo])` → 首个 `turn/start` 的 `item/tool/call`（`callId=exec-1a97e7c6-6e2b-4c5e-a8a2-953d8af5fa2a`）→ protocol-correct `{success:true,contentItems}` response → `thread/resume` → 第二个 `turn/start` 的 `item/tool/call`（`callId=exec-d2dca3d5-35f7-4ba5-a989-b15101a51720`）→第二次成功 response。两次 Turn 均 `completed`。这证明 catalog persistence、thread/turn/call 路由和 server-request response shape；正式实现仍须以自动化 L3 回归保护该契约。

## 后续用户裁决（2026-07-13）

用户明确将个人本机工具的两个限制改为：

1. `feishu.file_upload_and_send_current_channel` 可上传任意本机普通文件路径，不限 attachment/session/workspace 目录；当前 channel 和 App credential 绑定仍保留。
2. S05 不实现本地共享限流、429 自动退避或 retry queue；飞书明确 429 直接返回当前 Turn 的安全失败，由用户自行重试。

以上裁决已回写 S05，且替代本汇总中此前关于 allowlist 文件根、fd-safe containment 与 shared rate governor 的设计建议。
