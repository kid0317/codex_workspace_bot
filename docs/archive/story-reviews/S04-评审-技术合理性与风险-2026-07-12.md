# S04 技术合理性与风险独立评审

> **评审对象**：[S04：双区流式卡片展示](../../story/S04-双区流式卡片展示-设计.md) 与 [HLD v3.8](../../02-redesign-high-level.md)
> **评审类型**：独立、只读的架构/并发/状态机/失败恢复/数据一致性审查
> **评审日期**：2026-07-12
> **结论**：**Conditional — 不建议在下列 blocker 完成设计回写前开始实现。**

## 1. 审查范围与证据

本报告只评审 S04 设计是否能与当前 S03 Runtime、Worker、MySQL 生命周期和 HLD 命令契约正确衔接；不把尚未实现的 S04 当作已经存在的能力。

| 证据 | 用途 |
|---|---|
| [S04](../../story/S04-双区流式卡片展示-设计.md) §5—§9 | 模式分流、DisplayEvent、CardKit、companion 交付和验收契约。 |
| [HLD](../../02-redesign-high-level.md) §2.2、§4.1、§5.7、§6 | 同 channel Worker、`/cancel`/`/new` 控制面、总/idle timeout 和模式输出约束。 |
| [Runtime](../../../internal/codexapp/runtime.go#L211)、[Worker](../../../internal/worker/manager.go#L236)、[Storage](../../../internal/storage/messages.go#L130) | 当前 attempt 收尾、Worker 生命周期和批量条件状态迁移的真实接点。 |
| [旧 companion Segmenter](../../../../cc_workspace_bot/internal/session/segment.go#L44)、[旧发送循环](../../../../cc_workspace_bot/internal/session/worker.go#L334) | `[[SEND]]`、延迟、限流重试和逐段错误继续的现有语义。 |
| `go test ./...`、`go test -race ./... -count=1`（2026-07-12） | 当前 S03 基线可编译且 race 测试通过；它们没有证明 S04 尚未实现的路径。 |

## 2. 正面结论

1. **展示边界是正确且可实现的。**work 只投影 allowlisted completed `agentMessage`，并按 phase 分离 `commentary` 与 `final_answer`；companion 仅累积 final 并等待成功 Terminal（[S04:55-58](../../story/S04-双区流式卡片展示-设计.md#L55)）。这避免把 reasoning、工具输出和 delta 回吐给用户。
2. **CardKit 的未知结果处理有正确方向。**稳定 `open_uuid`、不可变 operation ledger、`SendUnconfirmed` 不重复可见发送，以及 final/settings 的 sequence 顺序，显著优于“超时就再发一张卡”（[S04:170-177](../../story/S04-双区流式卡片展示-设计.md#L170)）。L3b/L4 作为真实边界硬门也合理。
3. **companion 的用户语义比旧实现更完整。**final-only、delimiter lexer、保护 code/转义文本、per-batch internal token，以及逐段 trace 摘要，能在不把控制符泄漏给用户的前提下兼容模型输出波动（[S04:121-141](../../story/S04-双区流式卡片展示-设计.md#L121)）。
4. **验收层次足够清晰。**L1/L2 覆盖 deterministic state/adapter，L3/L4 强制验证飞书/CardKit 真实行为；这比依赖单一 mock 更可靠（[S04:203-257](../../story/S04-双区流式卡片展示-设计.md#L203)）。

## 3. 发现与可执行建议

### Blocker

| ID | 发现、触发条件与影响 | 可执行设计修复 | 是否需用户裁定 |
|---|---|---|---|
| B1 | **Terminal 的唯一裁决者、优先级和 delivery 取消句柄尚未定义。**S04 说 timeout、interrupt、runtime exit 与 `turn/completed` 走同一 Terminal path（[S04:155-157](../../story/S04-双区流式卡片展示-设计.md#L155)），却没有规定“timeout 与 completed 并发时谁赢”、谁拥有 compare-and-set，或 `/cancel` 在 Terminal 后、companion 分段延迟中如何找到 delivery context。HLD 要求命令直接到 Worker 控制面且不得与 active turn 竞争（[HLD:76](../../02-redesign-high-level.md#L76)）；现有 Runtime 以 first-wins `finish` 收尾（[runtime:356-365](../../../internal/codexapp/runtime.go#L356)），而现有 Worker 没有 command/delivery-handle 接口（[manager:362-417](../../../internal/worker/manager.go#L362)）。触发：total/idle timeout 与 completed 紧邻、`/cancel`/`/new` 在首段或段间 delay 到来、runtime exit 发生在 Terminal drain 后。影响：可能把已取消/超时结果当成功发送，或无法停止剩余文本，且下一 Batch 的释放时机不可证明。 | 增加 attempt-owned `TerminalArbiter`，明确原子状态 `Active -> Stopping(reason) -> Terminal(reason,status) -> Drained`，以及完整优先级表；`turn/completed=completed` 仅在 `Active` 时可成功，停止已声明后按明确规则处理。Worker 保存并只暴露一个 `DeliveryHandle{batchID, cancel, done}`；命令控制面在同一 worker mutex 下原子取消 active attempt 或 active delivery，等待 `done` 后才 `/new` 清 Thread/释放下一 Batch。补充 AT：timeout-vs-completed 两种先后顺序、cancel during first delay/send/retry、new during delivery、runtime exit during delivery、每种仅一个 DB 终态和零剩余发送。 | **否**（可按 HLD 的“取消优先、同 channel 串行”原则决定），但需把精确优先级写入设计。 |
| B2 | **companion 的“同一条件状态迁移”没有数据库原子性设计。**S04 要求 delivery summary 和最终内容在同一条件状态迁移中写入（[S04:129](../../story/S04-双区流式卡片展示-设计.md#L129)），但当前 `CompleteBatch` 对每条 Message 逐条 `UPDATE`、没有 transaction（[messages:143-153](../../../internal/storage/messages.go#L143)）。触发：一个 Batch 合并多条入站消息，第二条更新失败、连接丢失或进程退出。影响：同一次 Codex Turn 的 Message 会出现部分 `succeeded`、部分 `processing`/failed，无法通过 trace 解释，也会破坏后续重试与审计。 | 将 `CompleteBatch(..., CompanionDeliverySummary)` 设计为单一 repository transaction：对全部 IDs 以 `status='processing'` 条件更新，任何 rows-affected 不为 1 或任一步失败均 rollback；一次提交同时写所有行的 content、first-success message ID、duration 和一致的 delivery error code。定义事务失败后状态：保留 processing 并由 Worker 只作安全失败收尾，或用一个明确的 conditional `FailBatch` 全量迁移；不得逐行 best effort。为 DB failure / duplicate completion / partial rows-affected / retry 加 sqlmock + MySQL integration tests。 | **否**。 |

### High

| ID | 发现、触发条件与影响 | 可执行设计修复 | 是否需用户裁定 |
|---|---|---|---|
| H1 | **绑定前的 notification 缓存仍无上界，S04 的 64 条 inbox 无法覆盖它。**当前 `dispatch` 在 `turn/start` response 返回前直接 `append(a.pending, event)`（[runtime:304-320](../../../internal/codexapp/runtime.go#L304)）；S04 的 `Bound`/64 条管道是在 response 绑定后才建立（[S04:147-157](../../story/S04-双区流式卡片展示-设计.md#L147)）。触发：App Server 在 response 前连续发送 item/delta/completed 或异常 server 持续推送。影响：reader 可无界占用内存；也无法保证 pending 的顺序、上限和 Terminal 行为与新 DisplayEvent 一致。 | 把 pre-bind buffer 纳入同一 attempt 状态机：设置明确 byte/event cap（应同时限制 raw body bytes），只保留有 route 所需的事件；上限到达时原子进入 `prebind_backpressure`，关闭/interrupt 该 attempt 并保证 reader 不阻塞。`bindAttempt` 必须先投递 Bound，再按 seq 释放缓存；补充 response-before-events、response-after-超限、early Terminal、重复 early event 的 fake-server/race 测试。 | **否**。 |
| H2 | **“inbox 满时不丢 event”与有界非阻塞管道自相矛盾。**S04 同时要求 64 条普通 inbox、reader 不等待、inbox 满时“不丢 event”（[S04:155](../../story/S04-双区流式卡片展示-设计.md#L155)）。在没有 overflow store 或阻塞 reader 时，第 65 条 Item 不可能同时满足三者。影响：实现者会任意选择 drop/block/unbounded append，直接影响 final 是否可见、reader 健康及 AT-08 的可重复性。 | 改成精确定义：`TryPublish(Item)` 失败时，**当前展示 Item 不被 output state 接收**，但已由 S03 raw/event timeline 保存；attempt CAS 为 `Backpressured`，只投递一次容量为 1 的 Terminal(`presentation_backpressure`)，请求 interrupt，拒绝后续 Items，drain 已接收的 Items 后以安全失败终态结束。若产品要求“不丢展示 Item”，则必须指定一个有界、持久化的 spill queue 和恢复语义；不能只靠 channel。AT-08 断言上述唯一行为。 | **是**：需确认“保护 App Server 与确定性失败”是否接受展示 Item 被拒绝；否则须授权引入持久化/溢出队列（扩大 S04 范围）。 |
| H3 | **companion 没有总交付预算，模型可制造大量分段并长期占住同 channel Worker。**显式 delimiter 后每段最多 80 rune、且逐段延迟最高 2 秒（[S04:125-128](../../story/S04-双区流式卡片展示-设计.md#L125)），但没有 `max_segments`、总字节、总 delivery duration 或超限文案。触发：模型生成数百个 `[[SEND]]`，或错误把长表格逐句分段。影响：同 channel 后续用户消息被阻塞数十分钟；大量飞书 API 调用触发限流，和“任务/陪伴”体验都不相称。旧实现也没有上限，不能作为新运行时的容量保证。 | 增加 companion delivery budget：例如 `max_segments`、`max_total_bytes` 与 `max_delivery_duration`（均为配置且有安全上限）。明确超限策略：保留前 N 段后发送一条“剩余内容已合并/截断”文本，或退化为一条受飞书 150KB 限制的完整文本；在 summary/trace 标记 `companion_delivery_truncated`。加入超大量 delimiter、delay budget 到期、限流与取消交错测试。 | **是**：需要产品选择“完整性优先的一条长文本”还是“陪伴节奏优先的有限多段”。 |

## 4. 未证实项（不能以设计或本轮基线代替）

1. 飞书 CardKit v1 是否支持：稳定 open UUID 重试、entity-backed message 的同 ID PATCH、element text update、settings 关闭 streaming。S04 的 L3/L3b/L4 是正确门槛，但目前没有实测证据。
2. App Server 在 `turn/start` response 前发 event 的实际最大数量和顺序；因此 pre-bind cap 不能依赖“真实服务通常很快返回”。
3. 当前 Feishu SDK 对 rate-limit 错误码、retry-after 和 text message 单次上限的真实表现；L2 fake 与 LI-02 需分别证明。
4. companion lexer 的完整 grammar（嵌套/混用 Markdown fence、极端 Unicode、token collision）尚未实现；AT-14/15 是必要但仍需 property/fuzz 测试和 corpus。
5. 进程重启发生在 successful Terminal 与最后一次 `CompleteBatch` 之间时的持久化结果。S04 明确不恢复 active turn，但仍须定义 delivery 中止后的 Message 终态，不能留下无限期 `processing`。

## 5. 测试方案评估

S04 的 AT-00—AT-15、L3/L3b、LI-01/02 已覆盖 mapper、安全、CardKit ledger、delimiter 兼容和真实飞书边界，基础方向完整。要达到可实施，至少补充以下测试：

1. `TerminalArbiter` 的 timeout/completed/interrupt/runtime-exit 并发顺序矩阵，以及 command 取消发生在 Terminal 后 delivery 期间。
2. pre-bind cap 与 post-bind inbox-full 的 deterministic state transition；验证 reader 不阻塞、无无限内存增长、Terminal exactly-once。
3. companion delivery budget：N+1 段、总时间到期、取消/限流/普通发送错误组合；确保同 channel 下一 Batch 不提前开始。
4. `CompleteBatch` 的 MySQL transaction：一行失败、rows affected=0、commit 失败、重复调用和 crash/recovery 模拟，全部避免半批状态。
5. normal structured delivery trace 的 writer failure 和 trace-id 关联查询；不得依赖 debug raw payload 才能解释 partial delivery。

## 6. 最终结论

S04 的用户展示策略、CardKit 操作账本和 companion delimiter 设计整体合理，且比当前 S03 实现更严格。可是 **B1（终态/取消 ownership）与 B2（批量状态原子性）会直接影响“只在成功终态发送”和 MySQL 真实记录，属于开始实现前必须回写的 blocker**。H1/H2/H3 决定 reader 的背压安全和 companion 的服务容量，其中 H2、H3 需要明确产品取舍。

完成上述设计回写、补充对应 AT 后，可发起 blocker-only 复审；在此之前，本独立评审不建议保持“无条件 Ready”。
