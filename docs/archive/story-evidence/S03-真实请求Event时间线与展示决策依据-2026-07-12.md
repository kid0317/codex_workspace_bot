## 6. 索引字段检验与待补齐项

### 已满足

- `seq`、时间、generation、JSON-RPC class、method、RPC ID、Thread/Turn、attempt 和 route snapshot 已可记录或在无值时表达空身份。
- raw、event、outcome 可以按 `seq` 完整 join；当前 Turn 的 639 条 event 均可用 `turn_id` 过滤。
- 未知/背景 event 没有被丢弃：本次 22 条 `unrouted` 仍有 raw 与 event/outcome 证据。

### 当前缺口

| 缺口 | 事实证据 | 对展示设计的影响 | 后续最小改动 |
|---|---|---|---|
| event 索引未提取 `item_id` | 本次 raw 有 user/reasoning/command/file/agent 共 30 个 Item lifecycle，event JSONL 的 `item_id` 出现次数为 0。 | 无法只查 event 索引把 556 delta 聚合回 7 个 agent message，也无法把命令输出归到某个 command Item。 | 从 `params.item.id`、`params.itemId` 或 `params.item_id` 提取并始终写出 `item_id`。 |
| outcome 正常路径未写 `error:null` | 664 条 outcome 都有 seq/route/dispatch；成功 event 不含 `error` key。 | 读取方需要区分“字段省略”和“没有错误”，不符合 S03 的固定列契约。 | 每条 outcome 初始化 `error:null`，失败时替换为错误文本。 |
| event 的未知维度有时省略而不是 `null` | 进程级 response/通知没有完整的产品路由字段。 | SQL/JSONL 分析需要额外 `has()` 判断。 | 建立固定 event schema，所有维度字段预置为 `null`。 |
| 文本 delta 太细 | 一个 Turn 556 条 agentMessage delta。 | 一对一飞书 PATCH 会造成卡片限流、视觉噪声和高成本。 | 以 250–500ms、句末或字节阈值聚合；只 PATCH 合并后的快照。 |

这四项中，前三项是**调试索引质量**问题，不代表 raw payload 遗失；第四项是后续展示 Story 的产品/性能约束。

## 7. 后续展示建议

基于真实事件，而非仅凭协议猜测，后续可采用三层展示：

1. **用户卡片（默认）**：`turn/started` 创建；聚合后的 `item/agentMessage/delta` 更新正文；`turn/completed` 作为唯一终态。用户不需要看到 MCP、token、rate limit、hook 或逐条工具事件。
2. **可展开的工作轨迹**：按 `item_id` 聚合为 reasoning、commandExecution、fileChange、agentMessage 四类；先补 `item_id` 索引，再决定是否开放给用户。
3. **本地诊断时间线**：保留现有 raw/event/outcome，显示全部 664 条记录，含 route state、token/rate limit 和完整原文跳转。这是排障与协议演进工具，不是聊天 UI。

建议下一 Story 的展示范围先限于：工作卡片状态 + 聚合 agent 文本 + 最终状态；工具/推理/文件变更只做隐藏的结构化采集和本地诊断。这样既利用了真实流式价值，也不会把 556 个微粒度 delta 直接暴露为飞书噪音。
