## 1. 实际交付

S04 交付两种输出模式：work 在同一张 CardKit entity 上以全量 `Card.Update(card_json)` 展示灰色斜体进展、分隔线和最终正文；companion 不创建占位卡，只在成功终态后按 `[[SEND]]` 发送 plain-text 分段。

companion 交付由 `TerminalArbiter` 固定首个终态原因，由 `DeliverySlot` 覆盖 marker、首段发布、取消与 done。workflow JSONL 通过可返回错误的 writer 写入 batch/source trace、thread/turn、段序号、摘要、结果、消息 ID、重试和时间；写失败停止后续段并以 `companion_delivery_trace_incomplete` 收尾。

## 3. 发现的问题与永久改进

| 问题 | 根因分类 | 修复与预防 |
|---|---|---|
| CardKit 组件 Content API 发生参数错误、慢响应和 JSON 误展示 | 外部 SDK/API 契约与设计漂移 | 将真实成功的 full entity update 回写为正式主路径；不再把组件级 API 作为 S04 DoD。 |
| 一次 CardKit update 失败会使后续永远 PATCH | 缺失败路径测试 | `dropCardSession` 保留 entity session；新增回归测试确保下一次仍能尝试 CardKit。 |
| companion 成功终态与取消/发送交错没有明确所有权 | 缺并发状态边界 | Worker 引入 first-wins `TerminalArbiter` 和 `DeliverySlot`，控制命令等待 slot done。 |
| `slog.Info` 不能发现 workflow 文件写失败 | 缺可失败外部边界 | logging manager 暴露 error-returning writer；writer failure 停止余段并走稳定失败收尾。 |
| 编译产物在进程启动后被改写 | 缺运行顺序门禁 | 发布时单独构建，再启动隔离 PID，并记录二进制 mtime、启动时间、health/ready。 |

## 4. 用户裁定的残余边界

- companion empty/failed/restart-abandoned 的真实 Feishu 消息验收由于当前无法验证而推迟；实现与 focused unit tests 保留，后续验证窗口再补外部样本。
- AT-00--AT-24 不在本轮扩展成完整覆盖矩阵；已有行为与本轮新增控制面保持回归门禁。
- CardKit 失败一次后下一次真实 SDK Update 的注入式黑盒计数测试可在后续可靠性 Story 增强；当前 session-retention 回归测试与静态调用链已覆盖本次根因。
